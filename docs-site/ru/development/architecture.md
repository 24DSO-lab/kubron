# Архитектура

Kubron — это одно ядро на Go, две оболочки и один интерфейс на Vue. Страница объясняет, как это сочетается, чтобы вы ориентировались в репозитории. Решения, стоящие за устройством, записаны как ADR в [`docs/adr`](https://github.com/24DSO-lab/kubron/blob/master/docs/adr/README.md).

[[toc]]

## Общая картина

- **Ядро** (`internal/app`) содержит всю прикладную логику: кластеры, доступ к Kubernetes, Helm, Argo CD, аутентификацию и аудит. Wails оно не импортирует.
- **Две оболочки** запускают ядро. Оболочка **Desktop** — это `main.go` в корне репозитория, собранный Wails. Оболочка **Web** — `cmd/kubron-server`, HTTP-сервер. Имена методов в обеих одинаковы, поэтому один интерфейс работает поверх любой.
- **Один интерфейс** (`frontend/`, Vue 3) собирается под одну из двух целей: `desktop` или `web`.

```
 Интерфейс Vue 3 (frontend/)
        |  сборка под VITE_TARGET = desktop | web
        v
 Биндинги Wails (Desktop)         HTTP: POST /api/rpc/{method}, WebSocket /api/ws (Web)
        |                                   |
   main.go (оболочка)               cmd/kubron-server (оболочка)
        \_______________  _______________/
                        \/
                internal/app  (ядро)
        кластеры - Kubernetes - Helm - Argo CD - auth - аудит
                        |
              Store: файлы (Desktop)  |  PostgreSQL (Web)
```

## Структура репозитория

| Путь | Что там |

| `main.go`, `wails.json` | Оболочка Desktop (Wails) |

| `examples/ext-authenticator` | Минимальный внешний модуль |

## Ядро и оболочки

С оболочкой ядро общается только через небольшой интерфейс `Platform`: отправить событие интерфейсу, выбрать файл, открыть ссылку, сообщить возможности оболочки. Его реализуют оболочки Wails и web, а правило линтера запрещает ядру импортировать Wails (ADR-0002).

Оболочка сообщает **возможности** (диалог файла, режим port-forward, терминалы, оболочка узла, чтение локального kubeconfig, SSO), а интерфейс скрывает недоступное. В Desktop доступно всё локальное; веб-сервер часть функций отключает или меняет: например, port-forward идёт через прокси.

## Как Web общается с браузером

- **API.** `POST /api/rpc/{method}` с JSON-массивом аргументов. Диспетчер на рефлексии вызывает метод ядра, но только из allowlist.
- **События и терминалы.** Один WebSocket (`/api/ws`) несёт события в браузер, а бинарные кадры WebSocket — данные терминала.
- **Сессии.** Cookie плюс проверки CSRF и Origin. С PostgreSQL сессии общие для реплик. См. [Безопасность HTTP](/ru/server/http-security) и [Высокую доступность](/ru/server/ha).
- **События адресные:** они направляются сессии, а идентификаторы, которые видит браузер, создаёт сервер.

### Жизнь запроса

1. Браузер отправляет `POST /api/rpc/{method}` с cookie сессии и токеном CSRF. Сервер проверяет, что `Origin` совпадает с `Host` и что хост разрешён.
2. Он находит сессию (при нескольких репликах — через PostgreSQL) и роль пользователя.
3. Диспетчер вызывает метод ядра, но только если метод есть в allowlist.
4. Первое действие ядра — `authz(право)`: ваша роль Kubron, а в Web и роль в команде, должна разрешать действие. Отказ записывается в журнал аудита как **Denied**.
5. Ядро использует сессионный вид менеджера кластеров и подключается учётными данными кластера. Kubernetes RBAC проверяет вызов ещё раз.
6. Результат возвращается в браузер, разрешённое привилегированное действие записывается в журнал аудита, а последующие изменения приходят в браузер через WebSocket.

## Кластеры и доступ к Kubernetes

- Общий **пул подключений** держит informers для каждого кластера со счётчиком ссылок и временем жизни, поэтому списки и дашборд актуальны без постоянного опроса.
- Каждая пользовательская сессия получает **сессионный вид** менеджера: собственный активный кластер, терминалы, потоки логов и port-forward при общем пуле.
- Аутентификацию в кластерах выполняют **провайдеры учётных данных** (OIDC, AKS, EKS, GKE, `exec` в Desktop) за единым контрактом входа. См. [Подключение к Kubernetes](/ru/features/cluster-auth).
- Адреса, заданные пользователями (кластеры, провайдеры идентификации, репозитории Helm), проходят через **защиту от SSRF** (`netpolicy`).

## Хранилище и секреты

Ядро использует интерфейс `Store` с двумя реализациями: **файлы** в `~/.kubron` (Desktop и однопользовательский сервер) и **PostgreSQL** (сервисный режим). PostgreSQL внешний, его обслуживаете вы. Миграции схемы — обычные SQL-файлы, применяемые под advisory-блокировкой PostgreSQL, поэтому реплики, стартующие одновременно, не конкурируют. Уведомления между репликами идут через `LISTEN/NOTIFY`.

Секреты в базе (kubeconfig, пароли кластеров, токены Argo CD, секреты репозиториев Helm, сохранённые учётные данные входа) шифруются конвертным шифрованием на ключе `KUBRON_SECRET_KEY`. См. [Резервное копирование, восстановление и ротация ключа](/ru/server/backup).

## Мультитенантность

В Web-версии иерархия такая: организация, затем команда, затем кластер. Роли назначаются на команду, а кластер принадлежит ровно одной команде. См. [Команды](/ru/features/teams).

## Интерфейс

В `frontend/src/platform/` лежит тонкий слой (`api`, `events`, `files`), реализация которого выбирается при сборке через `VITE_TARGET=web|desktop`. Компоненты не вызывают биндинги Wails напрямую (это обеспечивает правило линтера). Представления ресурсов описываются данными в `frontend/src/resources`, а весь текст проходит через vue-i18n с английским как базовым языком.

## Основные внутренние пакеты

| Пакет | Назначение |
|---|---|
| `app` | Ядро: прикладные методы, общие для обеих оболочек |
| `k8s` | Доступ к Kubernetes, Helm и Argo CD, расчёты дашборда |
| `auth`, `teams`, `websession` | Локальные пользователи и роли, команды, общие веб-сессии |
| `credential`, `signin`, `idpnet`, `secrets` | Провайдеры входа в кластеры, ожидающие вызовы входа, HTTP-клиент провайдеров идентификации, конвертное шифрование |
| `store`, `pgstore`, `migrate`, `secretbox` | Интерфейс хранилища, хранилище PostgreSQL, миграции, шифрование секретов |
| `server`, `publicerr`, `streamid`, `termbuf` | HTTP-оболочка, безопасные для пользователя тексты ошибок, идентификаторы потоков, буферы терминалов |
| `replicaevents`, `jobs`, `clusterhealth` | Сообщения между репликами, задачи на одной реплике, проверки состояния кластеров |
| `pfproxy` | HTTP port-forward для Web-версии |
| `netpolicy` | Политика исходящих адресов (защита от SSRF) |
| `audit`, `logging`, `metrics` | Журнал аудита, журнал процесса, метрики Prometheus |
| `platform` | Реализации `Platform` для Wails и web |
