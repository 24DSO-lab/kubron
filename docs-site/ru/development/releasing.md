# Выпуск релизов

Страница для мейнтейнеров. Релиз выпускается одной командой, остальное делают GitHub Actions. Полный порядок со всеми подробностями — в [docs/releasing.md](https://github.com/24DSO-lab/kubron/blob/master/docs/releasing.md).

## Один номер версии

Один тег `vX.Y.Z` задаёт версию всего: десктопных файлов, образа `ghcr.io/24dso-labs/kubron:X.Y.Z`, Helm-чарта `oci://ghcr.io/24dso-labs/charts/kubron` версии `X.Y.Z` (его `appVersion` тоже) и имён файлов SBOM.

- Источник правды — `wails.json` (`info.productVersion`) и `frontend/package.json`. `scripts/release.sh` обновляет их сам, а workflow `release.yml` и `publish.yml` отказываются работать, если тег не совпадает с ними (для релиз-кандидата сравнивается базовая версия без суффикса).
- `deploy/helm/kubron/Chart.yaml` хранит заглушку `0.0.0-dev`. Версию чарта и `appVersion` подставляет `publish.yml` из тега, поэтому **править `Chart.yaml` при выпуске не нужно**.
- Пробная публикация без тега (`workflow_dispatch`) получает версию `0.0.0-dev.<sha>`, и такие образы не получают `latest`.

## Ветки

| Ветка | Назначение | Защита |
|---|---|---|
| `refactor` (или feature-ветки) | Рабочая ветка | Нет |
| `dev` | Готово к выпуску. CI запускается на каждый push | Запрет удаления и force-push |
| `master` | Выпущенный код. На ней ставятся теги `vX.Y.Z` | Только pull request, 7 обязательных проверок, запрет force-push |

GitHub — основной репозиторий. GitLab вторичный: в него отправляют без `--force`, а тянут всегда из GitHub.

## Порядок действий

1. **Коммит в `refactor`** и push на GitHub. Для внешних pull request из форков CI отдельно проверяет DCO.
2. **Журнал изменений.** Для каждого заметного пользователю изменения добавьте строку в раздел `## [Unreleased]` в `CHANGELOG.md` (Added, Changed, Fixed, Removed, Security). Эти строки станут описанием релиза.
3. **Слейте в `dev`**, когда всё готово, и дождитесь зелёного CI.
4. **Выпуск** из `dev`, с чистым рабочим деревом:

   ```bash
   scripts/release.sh 0.2.0 --dry-run   # проверки и предпросмотр описания, ничего не меняется
   scripts/release.sh 0.2.0             # сам выпуск (--watch: дождаться workflow)
   ```

5. **Готово.** Примерно через 10–20 минут релиз опубликован. После выпуска `refactor` равна `master`: продолжайте командой `git checkout refactor && git pull`.

Релиз-кандидат: `scripts/release.sh 0.3.0-rc.1`. Журнал изменений при этом не сворачивается, описание берётся из `[Unreleased]`, в файлах версия `0.3.0`, а релиз помечается как pre-release.

## Перед тегом

Тег ставится на `master`, но проверять нужно `dev`: pull request `dev` → `master` и тег затем идут по одному коммиту. Убедитесь, что для последнего коммита `dev` зелёное всё ниже. Часть workflow запускается только при изменении определённых путей, поэтому запустите их вручную, если последний push их не затронул (`gh workflow run <файл> --ref dev`).

| Проверка | Workflow |
|---|---|
| `go`, `go-race`, `windows`, `lint`, `frontend`, `build-web`, `licenses`, `headers` | `ci.yml` |
| `e2e` (Playwright и kind), `e2e-pg` (PostgreSQL, команды), `e2e-ha` (две реплики, потеря реплики) | `ci.yml` |
| `migrations` (вперёд и назад на PostgreSQL 16), `restore-check` | `ci.yml` |
| `deps-audit` (`npm audit`, osv-scanner, сроки исключений сканеров) | `ci.yml` |
| `vulncheck` (govulncheck): не блокирует, но найденные уязвимости с исправлением чините | `ci.yml` |
| `deploy` (`hadolint`, `chart`, `kind`) | `deploy.yml` (только при изменении нужных путей) |
| `e2e-firefox` | `e2e-firefox.yml` (только при изменении нужных путей) |
| CodeQL: последний прогон на `dev` зелёный, открытых алертов уровня high нет | `codeql.yml` |
| Пробная публикация сервера | `publish.yml` вручную: сборка, Trivy-ворота, SBOM, пакет чарта без push |

Кроме проверок:

1. **Журнал изменений.** Всё заметное пользователю описано в `[Unreleased]`. Изменения безопасности — в «Security». Несовместимые изменения схемы БД и значений чарта — в «Changed» с пометкой **Upgrade**: что сделать при обновлении.
2. **Исключения сканеров.** `python3 scripts/check-ignores.py` проходит, а записи в `.trivyignore` и `osv-scanner.toml`, срок которых истекает до конца следующей недели, пересмотрены.
3. **Миграции.** Для каждого нового файла в `internal/pgstore/migrations/`: есть `down`, схема совместима с прошлым релизом, а несовместимость явно записана в журнале изменений.
4. **Dependabot.** Открытые pull request обновлений безопасности для рабочих зависимостей влиты или осознанно отложены.
5. **Открытые issue с меткой `security`** (создаёт `scheduled-scan.yml`) разобраны.
6. `scripts/release.sh X.Y.Z --dry-run` проходит и показывает ожидаемое описание релиза.

### Почему часть job в зелёном прогоне «пропущена»

CI не повторяет работу над тем же содержимым. Результат тестов принадлежит **содержимому** (хешу git-дерева), а не коммиту: merge-коммит pull request, коммит после слияния и повышение `refactor` → `dev` → `master` имеют разные SHA, но одинаковые файлы. После полностью зелёного прогона job `Record verified tree` сохраняет отметку на 14 дней, а следующий прогон с тем же содержимым пропускает детерминированные job. Заново всегда выполняются `deps-audit`, `vulncheck`, `headers`, DCO, сборка по тегу и ручные запуски.

## Что делает `scripts/release.sh`

1. Проверяет, что вы в `dev`, дерево чистое, `dev` совпадает с GitHub, а тега ещё нет.
2. Переносит `[Unreleased]` в раздел `## [X.Y.Z] - дата`, обновляет ссылки внизу журнала изменений и версии в `wails.json` и `frontend/package*.json`, делает коммит `chore(release): vX.Y.Z` и отправляет его в `dev`.
3. Создаёт pull request `dev` → `master`, ждёт зелёных проверок и сливает его (merge commit).
4. Ставит аннотированный тег `vX.Y.Z` на `master` и отправляет его.
5. Продвигает `dev` и рабочую ветку `refactor` до `master` быстрой перемоткой. Другие ветки: `RELEASE_SYNC_BRANCHES="refactor feature-x"`; отключить: `RELEASE_SYNC_BRANCHES=" "`. Ветка с собственными коммитами не трогается, а скрипт подскажет слить вручную (`git merge github/master`); тогда возможен конфликт в `CHANGELOG.md`: оставьте в `[Unreleased]` только свои новые строки, а то, что уже свёрнуто в `[X.Y.Z]`, возьмите из `master`.

Если скрипт остановился (красная проверка, обрыв сети), устраните причину и запустите **ту же команду** снова: готовые шаги пропускаются.

## Что делает workflow `Release` (на тег `v*.*.*`)

1. `verify` выполняет тот же набор проверок, что `ci.yml`, на самом теге.
2. После зелёного `verify` параллельно:
   - **Десктоп** собирает Windows (x64), Linux (x64, плюс `.deb`) и macOS (universal), предварительно проверив, что тег совпадает с файлами версии.
   - **Сервер** (`publish.yml`) собирает образ, прогоняет Trivy-ворота (HIGH или CRITICAL с исправлением останавливают публикацию), создаёт SBOM образа, отправляет в ghcr.io, подписывает cosign (keyless) и добавляет аттестации происхождения и SBOM, затем упаковывает чарт, отправляет, подписывает и аттестует его вместе с его SBOM. `latest` получают только версии без суффикса (`-rc`, `-beta`). Уже опубликованная версия не перезаписывается: workflow падает.
3. `release` создаёт SBOM десктопа, `SHA256SUMS.txt` (файлы и все SBOM), аттестации и описание из журнала изменений с таблицей загрузок.
4. Создаёт релиз (для `v0.*` и релиз-кандидатов — pre-release) и публикует его. Релизы **неизменяемые**: файлы и тег после публикации не меняются.

Чтобы оставлять релиз черновиком для ручной проверки, задайте переменную репозитория `RELEASE_AUTO_PUBLISH=false`. Как проверить подписи и аттестации — в разделах [Развёртывание в Docker и Kubernetes](/ru/server/deploy#проверка-образа-и-чарта) и [Требования, загрузка и проверка](/ru/guide/installation#проверка-загрузки).
