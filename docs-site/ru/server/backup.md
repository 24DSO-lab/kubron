# Резервное копирование, восстановление и ротация ключа

Web-версия с PostgreSQL хранит состояние в двух частях. **Копируйте и храните их раздельно.**

| Что | Где лежит | Как копировать |
|---|---|---|
| Пользователи, команды, метаданные кластеров, журнал аудита, состояние Helm, веб-сессии, а также **зашифрованные** kubeconfig и секреты | База PostgreSQL | `pg_dump` или снимки хранилища |
| Ключ шифрования `KUBRON_SECRET_KEY` (и прежние ключи) | Secret Kubernetes или менеджер секретов | Копия в менеджере паролей или KMS, **не рядом** с копией базы |

Дамп базы без ключа бесполезен для секретов: kubeconfig, пароли кластеров, токены Argo CD и секреты репозиториев Helm расшифровать нельзя. Ключ без дампа бесполезен тем более. Копия ключа рядом с копией базы (в одном хранилище, с тем же доступом) лишает шифрование смысла. Чарт ключ **не генерирует**: потеря ключа означает потерю всех секретов в базе, а восстановить их можно только добавив кластеры заново.

## Резервное копирование

### База данных

Формат custom (`-Fc`) позволяет выборочное и параллельное восстановление:

```bash
pg_dump -Fc --no-owner --no-privileges -f kubron-$(date +%F).dump "$KUBRON_DATABASE_URL"
```

- Периодичность определяет допустимая потеря данных: для журнала аудита и составов команд обычно достаточно ежедневного дампа плюс WAL-архива или PITR средствами вашей СУБД или облака.
- Шифруйте копии на диске и при передаче, ограничьте доступ к ним. Они содержат хеши паролей, журнал аудита и шифротексты секретов.
- Веб-сессии (`web_sessions`) для восстановления не нужны: после него пользователи просто войдут заново. Чтобы не переносить их в тестовую среду, выполните на копии `TRUNCATE web_sessions;`.
- Чарт не создаёт CronJob для резервных копий. Запускайте `pg_dump` в объектное хранилище средствами своей инфраструктуры.

### Ключ

Храните ключ в менеджере паролей, KMS или запечатанном конверте, доступ у узкого круга людей. Сохраняйте:

- сам ключ вида `id:base64` и его `id`;
- **все прежние ключи, пока существуют копии базы, сделанные до их замены** (см. [Ротация ключа](#ротация-ключа-и-rekey)): копия читается теми ключами, которыми были зашифрованы её записи.

Узнать, какие `id` ключей нужны данным в базе:

```sql
SELECT 'clusters.kubeconfig' AS data, key_id AS key_id, count(*) FROM clusters WHERE kubeconfig_enc IS NOT NULL GROUP BY key_id
UNION ALL SELECT 'clusters.secret', secret_key_id, count(*) FROM clusters WHERE secret_enc IS NOT NULL GROUP BY secret_key_id
UNION ALL SELECT 'argo_tokens', key_id, count(*) FROM argo_tokens GROUP BY key_id
UNION ALL SELECT 'helm_repositories', secret_key_id, count(*) FROM helm_repositories WHERE secret_enc IS NOT NULL GROUP BY secret_key_id
UNION ALL SELECT 'cluster_credentials', secret_key_id, count(*) FROM cluster_credentials GROUP BY secret_key_id;
```

Записывайте `id` текущего ключа рядом с каждой копией базы (например, в имени файла): при восстановлении сразу видно, какой ключ достать.

## Восстановление

1. Создайте пустую базу и восстановите дамп:

   ```bash
   createdb kubron
   pg_restore --no-owner --no-privileges --exit-on-error -d kubron kubron-2026-11-01.dump
   ```

2. Создайте Secret с **тем же ключом** (тот же `id` и те же байты). Если в дампе остались записи под прежними ключами, добавьте их в `KUBRON_SECRET_KEY_PREVIOUS` (через запятую).
3. Установите чарт (или запустите сервер) с `KUBRON_DATABASE_URL`, указывающим на восстановленную базу. Миграции применятся сами, если дамп сделан на более старой схеме.
4. Проверьте: `/healthz` и `/readyz` отвечают `200`, вход под известной учётной записью проходит, кластер команды открывается.

При старте сервер читает по одной зашифрованной записи на каждый `id` ключа и **не запускается**, если ключа нет или он не подходит. Ошибка называет причину:

| Сообщение | Причина | Что делать |
|---|---|---|
| `…KUBRON_SECRET_KEY does not match…: …stored with encryption key "k1"…: ciphertext was encrypted with an unknown key` | В связке нет ключа с таким `id` | Добавьте ключ `k1` в `KUBRON_SECRET_KEY` (если он был текущим) или в `KUBRON_SECRET_KEY_PREVIOUS` |
| `…: failed to decrypt the secret` | `id` совпал, а байты ключа другие (ключ из другого окружения, опечатка) | Возьмите ключ, которым шифровались данные этой базы |

Текст ошибки не содержит ключа и расшифрованных данных. При выкладке с `RollingUpdate` реплика с неверным ключом не станет готовой, а старые реплики продолжат работать.

### Ключ утерян безвозвратно

Если ключ утерян, а база нужна (например, выгрузить журнал аудита), запустите сервер с `KUBRON_ALLOW_KEY_MISMATCH=1`: он стартует, пользователи и команды работают, а секреты кластеров недоступны. После этого добавьте кластеры заново с новыми kubeconfig. Постоянно держать этот режим включённым не следует.

## Ротация ключа и `rekey`

Новые записи шифруются текущим ключом, старые читаются прежними, пока не будут перешифрованы.

1. Создайте новый ключ с **новым `id`** (`id:base64`, 32 байта) и сохраните его в менеджере секретов **до** использования:

   ```bash
   echo "2026-11:$(openssl rand -base64 32)"
   ```

2. В Secret: новый ключ в `KUBRON_SECRET_KEY`, прежний в `KUBRON_SECRET_KEY_PREVIOUS` (через запятую, если прежних несколько). В чарте `secrets.keys.*` задают только **имена** записей внутри Secret; чтобы сервер читал прежний ключ, задайте `secrets.keys.previousSecretKey: KUBRON_SECRET_KEY_PREVIOUS` (по умолчанию пусто). Перезапустите все реплики (`kubectl rollout restart deploy/kubron`). Сервер стартует: связка читает данные обоими ключами.
3. Перешифруйте записи новым ключом. Команда читает базу из окружения сервера, поэтому запускайте её там, где оно есть:

   ```bash
   kubectl exec deploy/kubron -- /kubron-server rekey
   # re-encrypted with key "2026-11": 12 kubeconfigs, 3 cluster secrets, 2 Argo CD tokens, 4 Helm repository secrets, 5 sign-in credentials (0 still in legacy format)
   ```

   `rekey` повторяется безопасно: уже перешифрованные записи пропускаются. В образе нет оболочки, поэтому команда запускается напрямую либо одноразовым Job с теми же переменными окружения.
4. Убедитесь, что старый `id` больше не нужен: запросы из раздела [Ключ](#ключ) должны показывать только новый `key_id`.
5. Прежний ключ из `KUBRON_SECRET_KEY_PREVIOUS` можно убрать, но **храните его, пока живут копии базы, сделанные до `rekey`**: их записи зашифрованы им. Срок хранения ключа равен сроку хранения самой старой копии, которую вы захотите уметь восстановить.

`rekey` перешифровывает kubeconfig, секреты подключения кластеров, токены Argo CD, секреты репозиториев Helm и сохранённые учётные данные входа. Меняйте ключ по расписанию (например, раз в год) и при подозрении на компрометацию. Если ключ скомпрометирован, после `rekey` замените и сами секреты кластеров (токены, пароли): копии старее ротации остаются расшифровываемыми старым ключом.

## Проверка копий

Проект проверяет восстановление автоматически: job `restore-check` в CI выполняет `scripts/restore-check.sh`. Скрипт запускает сервер на исходной базе, делает `pg_dump`, восстанавливает его в пустую базу, запускает второй сервер с тем же ключом и проверяет, что вход проходит, а kubeconfig совпадает. Он же проверяет, что неверный ключ останавливает запуск с понятной ошибкой, что `KUBRON_ALLOW_KEY_MISMATCH=1` не отдаёт секреты, что ротация вместе с `rekey` работает, а в журналах нет токенов и байтов ключей.

Для запуска вручную нужны PostgreSQL, `pg_dump`, `pg_restore`, `psql`, `curl`, `jq` и `openssl`:

```bash
go build -o kubron-server ./cmd/kubron-server
PGHOST=127.0.0.1 PGUSER=postgres PGPASSWORD=postgres KUBRON_SERVER_BIN=./kubron-server scripts/restore-check.sh
```

Скрипт создаёт и удаляет базы `kubron_restore_src` и `kubron_restore_dst`.

Собственную проверку это не заменяет. **Раз в квартал** восстанавливайте последнюю настоящую копию на отдельном сервере с ключом из вашего менеджера секретов и проверяйте вход и доступ к кластеру. Только так видно, что копия и ключ действительно хранятся и сочетаются.

## Один пользователь и Desktop

Без PostgreSQL данные лежат в каталоге данных (`~/.kubron` или `KUBRON_DATA_DIR`): копируйте каталог целиком, как и раньше. Эта страница относится к режиму с PostgreSQL.
