## Что уже сделано и подтверждено в коде

- Каждый экспортируемый метод `App` начинается с `a.authz*` (`internal/app/app_auth.go`); новые методы классифицируются в `internal/server/methods.go`, тест `TestEveryAppMethodIsClassified` падает на неклассифицированном.
- RPC: Origin, `Content-Type: application/json`, cookie и CSRF-токен (`internal/server/http.go`); WebSocket: cookie и обязательный Origin (`internal/server/ws.go`, `terminal_ws.go`).
- Exec-плагины и локальные файлы в kubeconfig запрещены в веб-режиме (`internal/k8s/connection.go`).

## Сценарии ревью и pentest

Для каждого сценария: подготовка, что делать, ожидаемый результат. Критерий провала — любое иное поведение.

1. **Обход authz и IDOR.** Двумя пользователями из разных команд и ролей (`user`, `operator`, `admin`) вызвать каждый метод из `allowedMethods` с идентификаторами чужих кластеров, команд и терминалов (`internal/server/methods.go`). Ожидание: отказ `forbidden`, чужие данные не возвращаются. Отдельно: методы из `deniedMethods` недоступны из браузера.
2. **CSRF и Origin.** POST `/api/rpc/<метод>` с чужим `Origin`, без `Origin`, без `X-CSRF-Token`, с `Content-Type: text/plain`. Ожидание: чужой Origin — `403 forbidden_origin`; неверный тип содержимого — `415`; запрос без Origin пропускается проверкой источника (так работают не браузерные клиенты), но защищённый метод без cookie даёт `401 unauthenticated`, а с cookie и без верного `X-CSRF-Token` — `403 csrf`. Для WebSocket (сценарий 3) Origin обязателен: без него отказ.
3. **WebSocket и терминалы.** Открыть `/api/ws` и терминальный сокет без cookie, с чужим Origin, с Origin другого хоста. Открыть терминал чужого кластера; выполнить `exec` ролью без права `exec`; после выхода пользователя проверить, что поток закрылся.
4. **SSRF и NetworkPolicy.** Добавить кластер и IdP с адресами `169.254.169.254`, `127.0.0.1`, `[::1]`, `fd00:ec2::254`, а также задать их как `proxy-url` kubeconfig (адрес прокси тоже должен проверяться при соединении), хост с DNS-ответом во внутреннюю сеть (DNS rebinding: ответ меняется между проверкой и соединением). Ожидание: отказ политики адресов при каждом соединении. Из пода: `curl` на `169.254.169.254` и на недопустимый адрес должен блокироваться NetworkPolicy (при CNI, который её выполняет).
5. **Rate limit и блокировка входа.** Перебор пароля одного пользователя с разных адресов и несколько пользователей с одного; за прокси без и с `KUBRON_TRUST_PROXY` и подделанным `X-Forwarded-For`. Ожидание: блокировка растёт и общая между репликами; подделка заголовка без доверия не меняет ключ ограничения.
6. **Утечки секретов в логи и API.** Включить `debug`, выполнить вход, добавление кластера, обновление kubeconfig, ошибку соединения. Ожидание: в журнале, ответах и аудите нет паролей, токенов, `client-key`, ключа шифрования. `GetClusterKubeconfig` возвращает `<kubron:unchanged>` вместо секретов.
7. **Подмена адреса в kubeconfig.** Получить kubeconfig кластера, изменить `server`/`proxy-url` на свой, сохранить с плейсхолдером. Ожидание: отказ подстановки, сохранённый токен не отправляется на чужой адрес.
8. **Exec и локальные файлы в kubeconfig.** Загрузить kubeconfig с `exec`, `tokenFile`, `client-certificate: /etc/...`, `certificate-authority: /proc/...`. Ожидание: `ErrExecForbidden`/`ErrLocalFilesForbidden`. Отдельно: kubeconfig, где опасный контекст не выбран, а безопасный выбран; затем сменить контекст через `UpdateCluster` на опасный — ожидается отказ при сохранении (проверяется выбранный контекст). Исключение: `oidc-password` разрешён только с сохранёнными учётными данными IdP.
9. **Захват первого запуска.** На пустой БД: `SetupAdmin` без токена, с неверным токеном, параллельные запросы с верным токеном (гонка двух администраторов), после создания администратора повторный `SetupAdmin`. Ожидание: без токена `403`; одновременно создаётся ровно один администратор; повторный вызов отклоняется.
10. **Подмена cookie.** Со страницы на соседнем поддомене и на `*.pf.<baseDomain>` выставить `kubron_session` и `__Host-kubron_session` для родительского домена. Ожидание: по HTTPS сервер использует только `__Host-`; при `baseDomain`, вложенном в хост Kubron, чарт выдаёт предупреждение.
11. **Заголовок Host.** Запросы с неизвестным Host, с портом, с `X-Forwarded-Host`, с дублирующим Host. Ожидание: отказ для хостов вне `KUBRON_ALLOWED_HOSTS`; `Host: *.pf.<baseDomain>:443` маршрутизируется как поток.
12. **Прокси port-forward.** Открыть поток; из проксируемого приложения прочитать `document.cookie` и запросить `/api/session` основного origin. Повторно использовать ticket (на той же реплике — отказ `ErrUsedTicket`; на другой реплике — по описанию в остаточных рисках; зафиксировать результат). Подобрать идентификатор потока. Проверить `idleTimeout`/`maxDuration`.
13. **Ошибки 500.** Спровоцировать внутреннюю ошибку (недоступная БД, битый ввод). Ожидание: общий текст и request id, детали только в журнале.
14. **Права ролей.** Проверить таблицу ролей (`internal/auth/permissions.go`): `user` не видит значения Secret и Helm-значения (находка 6, право `secrets.read` есть только у `operator` и `admin`), `operator` не выполняет `write`, только `admin` управляет пользователями и командами.
15. **Цепочка поставки.** Проверить подпись и аттестации образа и чарта (`docs/deploy.md` «Проверка образа и чарта»); убедиться, что Trivy-ворота блокируют образ с исправимой HIGH/CRITICAL; что `.trivyignore` с просроченной записью роняет CI.

## Порядок повторного ревью

1. Перед каждым мажорным релизом пройти сценарии 1–15 на стенде с двумя репликами и записать результат здесь (дата, версия, исполнитель, отклонения).
2. Новые находки: серьёзность по влиянию (Высокий — захват сервера/кластера без учётки; Средний — раскрытие секрета или обход защиты при условии; Низкий — раскрытие деталей, усложнение атаки).
