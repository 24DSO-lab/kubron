# Выпуск релизов

Релиз выпускается одной командой. Всё остальное (CI, сборка под Windows/Linux/macOS, образ и чарт сервера,
SBOM, подписи, описание релиза, публикация) делают GitHub Actions.

## Один номер версии

Один тег `vX.Y.Z` задаёт версию всего: десктопных файлов, образа `ghcr.io/24DSO-lab/kubron:X.Y.Z`, чарта
`oci://ghcr.io/24DSO-lab/charts/kubron` версии `X.Y.Z` (его `appVersion` тоже `X.Y.Z`) и имён файлов SBOM.

- Источник правды — `wails.json` (`info.productVersion`) и `frontend/package.json`: `scripts/release.sh --prepare` обновляет их сам, а
  workflow'ы `release.yml` и `publish.yml` отказываются работать, если тег с ними не совпадает (для `-rc.N` сравнивается база
  без суффикса).
- `deploy/helm/kubron/Chart.yaml` хранит заглушку `0.0.0-dev`: версию чарта и `appVersion` подставляет `publish.yml` из тега
  (`helm package --version --app-version`). Править `Chart.yaml` при выпуске **не нужно**.
- Пробная публикация без тега (`workflow_dispatch`) получает версию `0.0.0-dev.<sha>`; такие образы не получают `latest`.

## Ветки

| Ветка | Назначение | Защита на GitHub |
|---|---|---|
| `refactor` (или feature-ветки) | рабочая: коммиты из IDE | нет |
| `dev` | готово к выпуску; сюда `refactor` попадает только через PR | только PR, те же обязательные проверки, что на `master`, включая Code scanning results (CodeQL, high и выше), запрет удаления и force-push |
| `master` | выпущенное; на нём ставятся теги `vX.Y.Z` | только PR, 7 обязательных проверок, запрет force-push |

GitHub — основной репозиторий. GitLab (`origin`) — вторичный: туда только отправляем
(`git push origin dev master --tags`, без `--force`), а тянем (`pull`) всегда из `github`.

## Порядок действий

1. **Коммит в `refactor`** из IDE, затем `git push github refactor`. Для внешних PR из fork CI отдельно проверяет DCO.
2. **CHANGELOG.** Если изменение заметно пользователю, добавьте строку в `CHANGELOG.md` в раздел
   `## [Unreleased]` (Added / Changed / Fixed / Removed / Security). Эти строки станут описанием релиза.
3. **Подготовка релиза в `refactor`.** Когда всё готово к выпуску, в `refactor` с чистым деревом:
   ```bash
   scripts/release.sh 0.2.0 --prepare   # [Unreleased] -> [0.2.0], версии в файлах, один коммит; ничего не пушит
   git push github refactor
   ```
   Дождитесь зелёного `refactor`. Подготовка делается **до** слияния в `dev`: так в `dev` уже лежит всё, что
   войдёт в тег, и после выпуска скрипту не нужно добавлять в `dev` новых коммитов.
4. **В `dev`.** Откройте pull request `refactor` → `dev` и дождитесь зелёных проверок, **включая CodeQL**: алерт уровня
   high блокирует слияние (проверка «CodeQL» от GitHub Advanced Security, это не job из `codeql.yml`, а результат анализа).
   Слейте PR (merge commit). После слияния на push в `dev` CI запускается ещё раз: дождитесь зелёного.
5. **Выпуск.** Из `dev`, с чистым рабочим деревом:
   ```bash
   scripts/release.sh 0.2.0 --dry-run   # проверки и предпросмотр описания, ничего не меняется
   scripts/release.sh 0.2.0             # сам выпуск (--watch: дождаться релизного workflow)
   ```
   Если шаг 3 пропущен, скрипт остановится и подскажет выполнить `--prepare`.
6. **Готово.** Через 10-20 минут релиз опубликован: `https://github.com/24DSO-lab/kubron/releases`.
   После выпуска `refactor` уже равна `master`: продолжайте работу с `git checkout refactor && git pull`.

## Чек-лист перед тегом

Тег ставится на `master`, но проверять нужно `dev`: PR `dev` → `master` и тег затем идут по тому же коммиту. До запуска
`scripts/release.sh X.Y.Z` (без `--dry-run`) убедитесь, что для последнего коммита `dev` зелёное **всё** ниже. Часть
workflow'ов запускается только по путям файлов: если последний push их не затронул, запустите их вручную
(`gh workflow run <файл> --ref dev`), иначе «зелёного» просто нет.

| Проверка | Где | Замечания |
| --- | --- | --- |
| `go`, `go-race`, `windows`, `lint`, `frontend`, `build-web`, `licenses`, `headers` | `ci.yml` | основные проверки кода |
| `e2e` (Playwright + kind) | `ci.yml` | веб-режим на файловом хранилище |
| `e2e-pg` | `ci.yml` | веб-режим на PostgreSQL, команды |
| `e2e-ha` | `ci.yml` | две реплики на одной PostgreSQL, потеря реплики |
| `migrations` | `ci.yml` | миграции вперёд и назад на PostgreSQL 16 |
| `restore-check` | `ci.yml` | `pg_dump` → пустая БД → тот же ключ читает секрет |
| `deps-audit` | `ci.yml` | `npm audit`, osv-scanner, сроки исключений в `.trivyignore` и `osv-scanner.toml` |
| `vulncheck` (govulncheck) | `ci.yml` | не блокирует, но откройте отчёт: найденные уязвимости с исправлением чините до релиза |
| `deploy` (`hadolint`, `chart`, `kind`) | `deploy.yml` | **по путям**: запустите вручную, если не менялись `Dockerfile`, `deploy/**` и т. п. |
| `e2e-firefox` | `e2e-firefox.yml` | **по путям** (CSP, заголовки); при сомнениях запустите вручную |
| CodeQL | `codeql.yml` | последний прогон на `dev` зелёный, открытых алертов уровня high нет |
| Пробная публикация сервера | `publish.yml` вручную, `push` выключен | `gh workflow run publish.yml --ref dev`: сборка, Trivy-ворота, SBOM, пакет чарта без push |

### Почему часть job'ов в зелёном прогоне «пропущена»

CI не повторяет работу над тем же содержимым. Результат тестов определяет **содержимое** (git tree hash), а не коммит:
merge-коммит PR, коммит после слияния и повышение `refactor` → `dev` → `master` имеют разные SHA, но одинаковые файлы.

- После полностью зелёного прогона `ci.yml` (или `deploy.yml`) job `Record verified tree` сохраняет артефакт
  `ci-verified-<tree>` (`deploy-verified-<tree>`) на 14 дней.
- Следующий прогон с тем же содержимым находит отметку и пропускает детерминированные job'ы; в сводке job `Changes`
  (`Tree already verified?` в `deploy.yml`) указана ссылка на прогон, который их выполнил. Пропущенный job считается
  зелёным, как и при пропуске по путям.
- **Всегда выполняются заново:** `deps-audit` и `vulncheck` (база уязвимостей меняется со временем), `headers`, DCO,
  **тег** (job `verify` в `release.yml` гоняет полный набор), ручной запуск (`workflow_dispatch`) и любой прогон,
  для которого отметки нет (другое содержимое, отметка старше 14 дней, ошибка поиска).
- Отметку пишут только прогоны push и PR **из этого же репозитория**, не из форков, и только если ни один job не
  пропущен, поэтому PR, пропустивший Go-job'ы по путям, отметки не оставляет.
- PR, который меняет только `frontend/` и `docs-site/` (без `*.go`), не запускает Go-job'ы (`go`, `go-race`,
  `migrations`, `restore-check`, `windows`, `lint`): Go-тесты не читают файлы фронтенда. Push, тег и ручной запуск
  идут полным набором.

Чтобы принудительно проверить заново, запустите workflow вручную: `gh workflow run ci.yml --ref dev`.

Кроме проверок:

1. **CHANGELOG.** В `[Unreleased]` описано всё заметное пользователю; изменения безопасности — в «Security», несовместимые
   изменения схемы БД и значений чарта — в «Changed» с пометкой **Upgrade** (что сделать при обновлении).
2. **Исключения сканеров.** `python3 scripts/check-ignores.py` проходит; записи в `.trivyignore` и `osv-scanner.toml`, срок
   которых истекает до конца следующей недели, пересмотрены.
3. **Миграции.** Если появились новые файлы в `internal/pgstore/migrations/`: у каждой есть `down`, схема совместима с
   прошлым релизом (см. «Откат»), а несовместимость явно записана в CHANGELOG.
4. **Dependabot.** Открытые PR обновлений безопасности для рабочих зависимостей влиты или осознанно отложены.
5. **Открытые issue с меткой `security`** (создаёт `scheduled-scan.yml`) разобраны.
6. `scripts/release.sh X.Y.Z --dry-run` проходит и показывает ожидаемое описание релиза.

## Что делает `scripts/release.sh`

**С `--prepare` (в `refactor`):** переносит `[Unreleased]` в раздел `## [X.Y.Z] - дата`, обновляет ссылки внизу
CHANGELOG и версии в `wails.json` и `frontend/package*.json`, делает коммит `chore(release): vX.Y.Z` (с `-s`).
Ничего не отправляет. Повторный запуск, когда всё уже подготовлено, ничего не делает. В `dev` и `master`
`--prepare` не работает.

**Без `--prepare` (в `dev`):**

1. Проверяет: вы в `dev`, дерево чистое, `dev` совпадает с GitHub, тега нет, в `dev` уже есть раздел `[X.Y.Z]`
   в CHANGELOG и версии `X.Y.Z` в `wails.json` и `frontend/package.json` (иначе останавливается и просит `--prepare`).
2. Ничего не коммитит и не пушит в `dev`: в `master` уходит ровно проверенное содержимое. Поэтому на выпуск не запускаются
   повторные прогоны CI, Deploy и CodeQL, которые раньше давал коммит `chore(release)`.
3. Создаёт pull request `dev` → `master`, ждёт зелёных проверок, сливает его (merge commit).
4. Ставит аннотированный тег `vX.Y.Z` на `master` и отправляет его.
5. Продвигает `dev` и рабочую ветку `refactor` до `master` (быстрая перемотка), чтобы в `refactor`
   был релизный коммит и свёрнутый CHANGELOG. Другие ветки: `RELEASE_SYNC_BRANCHES="refactor feature-x"`,
   отключить: `RELEASE_SYNC_BRANCHES=" "`. Если в ветке есть свои коммиты, она не трогается:
   скрипт подскажет, что слить вручную (`git merge github/master`).
   В этом случае возможен конфликт в `CHANGELOG.md`: оставьте в `[Unreleased]` только свои новые
   строки, а то, что уже свёрнуто в `[X.Y.Z]`, возьмите из `master`.

Если скрипт остановился (красная проверка, обрыв сети), исправьте причину (для проверок:
коммит в `refactor`, слияние в `dev` и push) и запустите **ту же команду** снова: готовые шаги пропускаются.

Предрелиз: `scripts/release.sh 0.3.0-rc.1 --prepare`, затем так же через `dev`. CHANGELOG при этом не переносится, описание берётся из
`[Unreleased]`, в файлах версия `0.3.0`, релиз помечается как pre-release.

## Что делает workflow `Release` (запускается на тег `v*.*.*`)

1. `verify`: тот же набор проверок `ci.yml`, что и на ветке (тег не полагается на то, что CI уже видел коммит).
2. После зелёного `verify` параллельно:
   - **десктоп** (`build`): проверка версии тега, сборка Windows (x64), Linux (x64, плюс `.deb`), macOS (universal);
   - **сервер** (`server` → `publish.yml`): сборка образа, Trivy-ворота (HIGH/CRITICAL с исправлением останавливают
     публикацию), SBOM образа (syft, SPDX), push в ghcr.io, подпись cosign (keyless) и аттестации (происхождение и SBOM),
     затем пакет чарта, его push, SBOM (CycloneDX), подпись и аттестации. `latest` получают только версии без суффикса
     (`-rc`, `-beta`). Уже опубликованная версия не перезаписывается: workflow падает.
3. `release`: SBOM десктопа по `go.mod`/`package-lock.json`, `SHA256SUMS.txt` (файлы и все SBOM), аттестации, описание из
   `CHANGELOG.md` (раздел версии; для rc без раздела: `[Unreleased]`) с таблицей загрузок (`.github/release-footer.md`) и
   ссылкой на сравнение.
4. Создаёт релиз (для `v0.*` и rc: pre-release) и публикует его. Релизы неизменяемые (Immutable): файлы и тег после
   публикации не меняются.

Состав релиза: десктопные файлы, `.deb`, `SHA256SUMS.txt`, `kubron-sbom_<версия>_{image.spdx,chart.cdx,desktop.cdx}.json`.
Как проверить подписи и аттестации: `docs/deploy.md`, раздел «Проверка образа и чарта».

Оставлять релиз черновиком для ручной проверки: переменная репозитория `RELEASE_AUTO_PUBLISH=false`
(Settings → Secrets and variables → Actions → Variables).

## Разовая настройка

1. **GitHub CLI:** `winget install GitHub.cli`, затем `gh auth login`.
2. **Защита `dev`:** создайте ruleset `protect-dev` (Branch, цель `dev`) с правилами Restrict deletions,
   Block force pushes, Require a pull request и теми же Require status checks, что в защите `master`. Обязательно
   добавьте Require code scanning results: инструмент CodeQL, Security alerts «High or higher». Без этого правила красный
   CodeQL пропускает PR `refactor` → `dev` и останавливает релиз только на PR `dev` → `master`. Ruleset
   `protect-main-branches` остаётся для `master`.
3. **Защита `master`** остаётся как есть. Скрипт выпускает PR с merge commit.
4. **Не выключайте rulesets и не делайте force-push в `master`/`dev`**, в том числе `git push --all --force`
   и `--mirror`: это уже один раз откатило `master` назад.

## Если что-то пошло не так

- **Проверки PR `dev` → `master` красные:** исправьте в `refactor`, слейте через PR в `dev`, дождитесь зелёного
  и запустите команду снова. Если красный только CodeQL, откройте алерты в Security → Code scanning: high блокирует слияние.
  Упавший e2e без изменений в коде сначала перезапустите («Re-run failed jobs»); тот же тест красный повторно: это не флейк.
- **Упал workflow Release:** на странице запуска «Re-run failed jobs». Если упал после создания
  черновика: удалите черновик в Releases и перезапустите запуск.
- **Упала публикация сервера (`server`) посреди работы** (образ уже в ghcr.io, а чарт нет, или наоборот): повторный запуск
  откажется перезаписывать версию. Удалите частично опубликованную версию в Packages (`kubron` и `charts/kubron`, версия
  `X.Y.Z`, а также тег `latest`, если он указывает на неё) и перезапустите «Re-run failed jobs».
- **Trivy остановил публикацию:** обновите уязвимую зависимость или базовый образ. Если уязвимость недостижима, добавьте запись
  в `.trivyignore` с обоснованием и сроком (`scripts/check-ignores.py` проверит формат); это решение должен подтвердить второй
  человек в PR.
- **Ошибка в опубликованном релизе:** Immutable-релиз изменить нельзя. Выпустите следующую версию
  (`0.2.1`); править можно только название и описание релиза. Образ и чарт тоже не переписываются: исправление всегда новая версия.
- **Срочное исправление (hotfix):** ветка от `master`, PR в `master`, затем `git merge github/master`
  в `dev` (скрипт требует, чтобы в `dev` были все коммиты `master`).
- **Нет `gh` или не нужен автомат:** вручную то же самое: `node scripts/changelog.mjs roll X.Y.Z`,
  версии в двух файлах, коммит в `dev`, PR `dev` → `master` с merge commit, `git tag -a vX.Y.Z`
  на `master` и `git push github vX.Y.Z`.

## Откат

Откат сервера — это откат **кода** (образ и чарт), а схему БД он не трогает. Поэтому порядок такой.

**1. Решите, совместима ли схема.** Сервер применяет миграции при старте под advisory-lock, а более старый бинарник работает
с более новой схемой в режиме совместимости (ADR-0016, `docs/ha.md`). Правило для авторов миграций: новая схема обязана
работать с кодом **предыдущего** релиза (добавляйте, а не переименовывайте и не удаляйте; удаление — только в следующем релизе).
Исключение допускается лишь с пометкой **Upgrade** в CHANGELOG, там же описан откат.

**2. Совместимая схема (обычный случай): `helm rollback`.**

```sh
helm -n kubron history kubron
helm -n kubron rollback kubron <ревизия> --wait --timeout 5m
```

Веб-сессии лежат в PostgreSQL и переживают откат; открытые терминалы, логи и port-forward открываются заново. Если установка
управляется GitOps (Argo CD, Flux), откатите коммит с версией в Git, а не выполняйте `helm rollback` вручную: иначе
контроллер вернёт всё обратно. Secret с ключом (`secrets.existingSecret`) Helm не откатывает: он не принадлежит релизу.

**3. Несовместимая схема: откат из резервной копии, а не `down`.**

- У каждой миграции есть `*.down.sql`, и CI проверяет цикл вперёд → назад → вперёд (`scripts/check-migrations.sh`). Но
  **сервер `down` никогда не применяет**, а сами скрипты деструктивны: удаляют таблицы и колонки вместе с данными, записанными
  уже после обновления.
- Поэтому откат несовместимого релиза: остановить серверы (`replicaCount: 0`), восстановить БД из копии, снятой **перед**
  обновлением (`docs/backup.md`; делайте её перед каждым обновлением, меняющим схему), затем `helm rollback`.
- Применять `down` вручную допустимо только в окне обслуживания, на копии базы или когда точно известно, что удаляемые
  структуры пусты: скрипты выполняются в обратном порядке версий, каждый в своей транзакции, и после каждого нужно удалить
  соответствующую запись в `schema_migrations` (сверьте структуру таблицы: `\d schema_migrations`), иначе при следующем старте
  сервер решит, что миграция применена. Ключ шифрования при откате не меняется: если вместе с релизом менялся ключ
  (`rekey`), нужен прежний ключ из `KUBRON_SECRET_KEY_PREVIOUS`.
- Если в релизе строка **Upgrade** требует `strategy.type: Recreate`, откат делается так же, с остановкой всех реплик.

**4. Десктоп.** Релизы неизменяемы: «откат» — выпуск следующей версии с исправлением; пользователям до этого можно
рекомендовать предыдущий релиз.
