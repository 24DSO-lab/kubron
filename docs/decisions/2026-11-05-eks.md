# Решения: провайдер AWS EKS (тикет B.7a)

Статус всех решений ниже: **ждёт ревью человеком**.
Зона: `internal/credential/providers/eks/`, регистрация в `internal/app/credbroker.go`, ключи i18n `credEKS*` и `credential.field.eks*`.
Первоисточники: `awscli/customizations/eks/get_token.py`, `awscli/botocore/utils.py` (SSOTokenFetcher), `botocore/tokens.py`,
`botocore/auth.py`, модели сервисов `sso`/`sso-oidc`/`sts` из botocore, `kubernetes-sigs/aws-iam-authenticator` (`pkg/token/token.go`),
исходники `aws-sdk-go-v2` v1.47.5 (`aws/signer/v4`).

## E-01. Долгоживущие ключи AWS хранятся зашифрованно (область user)

- **Проблема.** Токен EKS живёт 14 минут и выпускается заново каждый раз. Подпись требует секретного ключа, поэтому ключ должен
  быть доступен серверу долго. Хранить нельзя только пароль личной учётной записи (ADR-0018, раздел 3), но ключ AWS по сути такой же секрет.
- **Варианты.** (а) не хранить, спрашивать каждые 14 минут: неприменимо; (б) хранить только временные ключи: неудобно, сроки 1-12 ч;
  (в) хранить введённые ключи в `Saved` (шифрует Broker, ADR-0008), область `user`, и рекомендовать временные ключи и SSO.
- **Решение.** (в). `Saved` = JSON `{v:1,type:"keys",accessKeyId,secretAccessKey,sessionToken?,region?,cluster?,principal?}`. Для SSO
  `{v:1,type:"sso",...}`: регистрация клиента, токены и кэш ролевых ключей. Провайдер сам ничего не шифрует и не пишет на диск.
- **Последствия.** Утечка БД вместе с мастер-ключом раскрывает ключи AWS пользователей. Смягчение: IAM-пользователь с минимальными правами
  (для входа в кластер нужна только возможность `sts:GetCallerIdentity`, она есть у любого пользователя), ротация ключей, предпочтение SSO (ключи живут около часа)
  или `session` (временные ключи). Это нужно написать в руководстве пользователя (тикет C.5).
- **Отмена.** Убрать ветку `savedKeys` из `fromSaved` и `Save` из `continueKeys`: провайдер будет просить ключи заново при каждом входе.

## E-02. Диалог: способ входа вводится словом, session-токен отдельным путём

- **Проблема.** Контракт v1 заморожен: `Field{Name, Secret}`, необязательных полей и выбора из списка нет. Диалог (`challengeView.fieldsFilled`) не
  даёт отправить форму с пустым полем, даже секретным. Поэтому «sessionToken, может быть пустым» из задания в одной форме невозможен, а выбор
  между ключами и SSO нечем выразить.
- **Варианты.** (а) одна форма с sessionToken: постоянные ключи нельзя ввести; (б) первый шаг со словом-выбором `eksMethod` (`keys`, `session`,
  `sso`), дальше форма под выбор; (в) менять диалог (чужая зона).
- **Решение.** (б), три шага на `secret-fields`: 1) `eksMethod` (+ `eksRegion`, `eksClusterName`, если kubeconfig их не задал);
  2) `accessKeyId`, `secretAccessKey` (+ `sessionToken` для `session`) или поля SSO `eksSsoStartUrl`, `eksSsoRegion`, `eksAccountId`, `eksRoleName`;
  3) для SSO `device-code`. Ключи ответа: `accessKeyId`, `secretAccessKey`, `sessionToken` (общие подписи) и `eks*` (подписи с префиксом провайдера).
  Ключи `ASIA...` без session-токена отвергаются как `ErrInvalidAnswer` (попытка не расходуется).
- **Последствия.** Слово в поле вместо выбора из списка: неудобно. **Просьба в зону диалога (A.5):** поддержать в `Field` необязательность и выбор
  (`options`) или принять, что провайдер выбирает способ по `Params`. После этого провайдер сводится к двум шагам; сообщения и ключи `eks*` останутся.
- **Отмена.** Убрать шаг `stepMethod`, оставив один способ входа.

## E-03. Ключи проверяются при каждой выдаче токена, с офлайн-запасом

- **Проблема.** Подпись токена не требует сети, но отозванные или просроченные ключи дают токен, который кластер отвергает с 401, а Broker
  при 401 лишь сбрасывает кэш и снова вызывает `Begin`: пользователь застрял бы без нового вызова.
- **Решение.** `Begin` с сохранёнными ключами вызывает STS `GetCallerIdentity` (≈ раз в 14 минут, через `Env.HTTP`). Отказ
  (`InvalidClientTokenId`, `SignatureDoesNotMatch`, `ExpiredToken` и др.) приводит к вызову и `Save: []byte{}`. Если AWS недоступен (сеть, 5xx,
  429), токен всё равно подписывается локально, принципал берётся из `Saved`. С `role-arn` проверкой служит `AssumeRole`.
- **Последствия.** Один лёгкий запрос в STS каждые 14 минут на пользователя. Сбой AWS не ломает вход при действующих ключах.
- **Отмена.** Убрать вызов `identity` из `fromSaved`: токен будет выпускаться без сети, а отозванные ключи не будут замечены.

## E-04. AssumeRole при каждой выдаче, без кэша временных ключей

- **Решение.** `RoleSessionName` = `kubron`, срок по умолчанию (как в задании; aws-cli использует `EKSGetTokenAuth`, но это имя только для аудита
  в CloudTrail). Токен подписывается временными ключами; принципал: ARN роли из kubeconfig. Временные ключи не сохраняются.
- **Последствия.** Один `AssumeRole` каждые 14 минут. Отказ роли (`AccessDenied`) при вводе: `ErrAnswerRejected`; при выдаче из сохранённых
  ключей: обычная ошибка (не `ErrInvalidGrant`, запись не стирается, новый вызов не создаётся): проблема в политике роли, а не в ключах.
  Роль из kubeconfig должна принадлежать тому же разделу AWS, что и регион (`aws`, `aws-cn`, `aws-us-gov`).
- **Отмена.** Кэшировать временные ключи в `Saved` до `Expiration - 16 мин`, как сделано для SSO.

## E-05. IAM Identity Center (SSO)

- **Что сделано по первоисточнику.** `RegisterClient` (public, scope `sso:account:access`, это `_AUTH_GRANT_DEFAULT_SCOPE` и scope
  `sso_registration_scopes` в aws-cli), `StartDeviceAuthorization`, `CreateToken` (grant `urn:ietf:params:oauth:grant-type:device_code`),
  `GetRoleCredentials` (`x-amz-sso_bearer_token`, `expiration` в миллисекундах). Интервал и `slow_down` (+5 с, максимум 60 с) как в aws-cli и RFC 8628.
  Ссылка из ответа проходит `idpnet.CheckURL` (https в вебе).
- **Обновление токена.** `CreateToken` с `grantType=refresh_token` описано в модели сервиса и используется `botocore.SSOTokenProvider`.
  Refresh-токен выдаётся, если клиент зарегистрирован со scope, поэтому scope передаётся. **Живую проверку на реальном IAM Identity Center
  провести не удалось (нет сети до AWS в среде разработки)**: логика проверена только на тестовом сервере. Любой отказ при обновлении
  (`invalid_grant`, срок регистрации клиента `clientSecretExpiresAt`, нет refresh-токена) даёт повторный вход, а не ошибку.
- **Кэш.** Ролевые ключи (≈ 1 ч) хранятся в `Saved` и используются, пока действуют ещё 16 минут (14 минут токена и запас); тогда токены
  выдаются без сети. Регистрация клиента не переиспользуется между входами (на каждый вход новая, как у `aws sso login` без сессии).
- **Повторный вход.** Требует снова ввести 4 поля SSO (запись стирается по контракту). Улучшение: стартовать устройство по сохранённой
  конфигурации. Не сделано, чтобы не нарушать правило «непригодный `Saved` стирается».
- **Отмена.** Убрать шаги `stepSSO`/`stepDevice` и метод `sso`; остальные способы не затрагиваются.

## E-06. Расхождение с aws-cli: порядок двух параметров запроса

- Go SDK (и aws-iam-authenticator на нём) сортирует параметры presigned-URL: `X-Amz-Security-Token` идёт перед `X-Amz-SignedHeaders`;
  botocore ставит его после. Подпись считается по отсортированному canonical query, значения и подпись одинаковы. Верификатор authenticator
  разбирает запрос как набор параметров. Без session-токена токены совпадают побайтово (тест на эталонах botocore,
  `testdata/golden_tokens.json`, `testdata/gen_golden.py`).
- Все константы совпали с первоисточником: префикс `k8s-aws-v1.`, base64url без дополнения, `X-Amz-Expires=60`, подписанные заголовки
  `host;x-k8s-aws-id`, срок токена 14 минут (`TOKEN_EXPIRATION_MINS`), `Action=GetCallerIdentity&Version=2011-06-15`.
  В задании было `https://sts.<region>.amazonaws.com/?Action=...`: так и сделано (региональный endpoint, для `cn-*` `amazonaws.com.cn`;
  для `us-gov-*` `amazonaws.com`). Глобальный `sts.amazonaws.com` не используется.

## E-07. Что провайдер не делает

- **Учётные данные сервера не используются никогда**: ни переменные окружения, ни `~/.aws`, ни профили, ни IMDS/контейнерные эндпоинты, ни
  цепочки SDK. Пакет не импортирует `os`, `config`, `credentials`, `feature/ec2/imds` (проверяется тестом по импортам и тексту исходников и
  тестом по поведению: на «заражённой» машине токен не выдаётся без ввода пользователя). `profile` из kubeconfig игнорируется.
- **Сеть только через `Env.HTTP`**; своих клиентов и транспортов нет. Адреса строятся из проверенного региона (`sts.<region>`, `oidc.<region>`,
  `portal.sso.<region>`); адреса из kubeconfig не запрашиваются. Если `Env.HTTP == nil`, ошибка, а не клиент по умолчанию.
- **Регион проверяется регулярным выражением**, чтобы значение нельзя было превратить в чужой хост (`us-east-1.evil.example`, `/`, `@`, `:`).
- **Не поддержаны** (дают `ErrUnsupported`, Broker переходит на exec/manual): неизвестное значение `authenticator`, изолированные разделы
  (`iso*`), неверные значения в kubeconfig (регион, имя кластера, ARN роли, роль не того раздела). `--cluster-id` (Outposts) и ключи
  `-r`/`--role` вне разобранных `Describe` не учитываются: имя кластера спрашивается у пользователя.

## E-08. Зависимости (go.mod и go.sum не изменялись)

Нужны, `go mod tidy` и `go mod verify` выполняет человек с сетью:

| Модуль | Версия | Лицензия |
| --- | --- | --- |
| `github.com/aws/aws-sdk-go-v2` | v1.47.5 | Apache-2.0 |
| `github.com/aws/smithy-go` | v1.28.7 (косвенная, требуется SDK) | Apache-2.0 |

Используются только пакеты `aws` и `aws/signer/v4`. Версии выбраны по последним тегам корневых модулей на момент работы; тесты прогнаны на них
(исходники с GitHub, сборка с `replace` в отдельном модуле). Лицензии входят в список CI (`Apache-2.0`). Транзитивные зависимости SDK
для этих пакетов только из тех же двух модулей.
