# Решения: вход пользователя Google в GKE (тикет B.7b, пункт 5)

Статус: **ждёт ревью человеком**.

Область: `internal/credential/providers/gke/user.go`, `BrokerOptions.GKEOAuth`, переменные сервера
`KUBRON_GKE_OAUTH_CLIENT_ID` и `KUBRON_GKE_OAUTH_CLIENT_SECRET`.

Условия пункта (слияние промпта 8 и OAuth-клиент Google): промпт 8 влит в `refactor`; о наличии клиента сообщил Vadim
командой выполнить пункт. Сам клиент в Google Cloud я не видел и не регистрировал: **его надо создать и проверить
вживую**.

## 1. Откуда берётся OAuth-клиент

**Проблема.** `Descriptor.Params` приходит из kubeconfig и может содержать чужие значения; у плагина GKE параметров
клиента нет. Читать окружение провайдеру нельзя (правило 2).

**Варианты.** (1) Params, как `web.client-id` у OIDC. (2) Конструктор провайдера `NewWithUserOAuth`, значения из
конфигурации сервера.

**Решение.** Вариант 2. `BuildBroker` получает `BrokerOptions.GKEOAuth`, сервер заполняет его из
`KUBRON_GKE_OAUTH_CLIENT_ID/SECRET`; адрес возврата это `KUBRON_PUBLIC_URL` + `/auth/cluster/callback` (тот же маршрут,
что у OIDC). Клиент и секрет не попадают в Descriptor, события, API и адрес браузера. Конструктор проверяет значения
(печатные ASCII, адрес https или http на loopback, фиксированный путь, без query, fragment и userinfo).

**Последствия.** Клиент один на сервер. На десктопе настройки клиента нет (там GKE входит по ключу или через плагин).
Секрет живёт в окружении сервера, как `KUBRON_SECRET_KEY`.

**Отмена.** Не задавать переменные: провайдер ведёт себя как до этого изменения.

## 2. Какие способы возврата браузера

- Веб с `KUBRON_PUBLIC_URL`: `browser-callback`. Broker подставляет ID вызова в `state`, сервер передаёт адрес
  возврата в `Continue`. Нужен клиент типа Web application с этим redirect URI.
- Остальное (веб без URL, десктоп): `paste-redirect` с адресом `http://127.0.0.1:<порт 49152..65535>`, на котором
  ничего не слушает; пользователь вставляет адрес страницы. Нужен клиент типа Desktop app.
- **Не сделано:** локальный слушатель на десктопе (loopback, как в OIDC). У OIDC он хранит сокет в памяти процесса;
  для GKE это отдельный объём работы, а на десктопе у GKE есть и плагин, и ключ.

## 3. ID-токен без проверки подписи

ID-токен нужен только для адреса почты (имя в аудите и `Principal`). Он приходит напрямую от Google по TLS в ответ на
запрос этого клиента, поэтому подпись по OpenID Connect Core 3.1.3.7 (п. 6) можно не проверять. Проверяются `iss`,
`aud`, `azp`, `exp`, `nonce`, `email_verified` и форма адреса. Это упрощает код и убирает загрузку ключей Google
(лишний сетевой обмен). **Последствие:** при компрометации TLS-канала до Google подделка токена возможна, но тогда
скомпрометирован и сам токен доступа. **Отмена:** добавить проверку подписи по JWKS Google через `Env.HTTP`.

## 4. Запрос `access_type=offline` и `prompt=consent`

Google выдаёт refresh-токен только при таком запросе. Побочный эффект: окно согласия показывается при каждом входе.
Токен хранится в `Saved` (шифрует Broker) вместе с адресом почты и идентификатором клиента: токен другого клиента Google
не принимает, поэтому при смене клиента запись стирается без запроса к Google. Если Google ответил без refresh-токена,
`Save` не создаётся (вход работает до конца жизни токена, около часа).

**Отмена.** Убрать `access_type` и `prompt`: токены не будут сохраняться.

## 5. Как выбирается способ входа

Выбора в диалоге нет (контракт v1 заморожен, вида вызова «выберите способ» нет). Правило: есть клиент Google, новый
вход идёт через аккаунт Google, иначе через ключ. Ранее сохранённый ключ продолжает работать; ключ, который Google
перестал принимать, запрашивается снова как ключ, а не заменяется входом через Google. **Следствие:** при настроенном
клиенте нельзя первым способом выбрать ключ сервисного аккаунта; чтобы вставить ключ, нужно снять переменные или сначала
сохранить ключ при выключенном клиенте. Если это важно, нужен новый вид вызова (правка контракта).

## 6. Сетевой обмен

Запросы к `TokenURL` идут через `Env.HTTP.Do` с контекстом вызова (отмена прерывает запрос), без `oauth2.Config` и без
своего транспорта. Адрес авторизации (`AuthURL`) и токена (`TokenURL`) это константы. Тест исходников по-прежнему
запрещает `os`, `net`, `log`, SDK облаков и пакет `golang.org/x/oauth2/google`; в список импортов добавлены только
`crypto/rand`, `crypto/sha256`, `crypto/subtle`, `encoding/base64`, `net/url`, `strconv` и из `net/http` constructor
запроса и константы.

## 7. Ограничения

- Scope `cloud-platform` чувствительный: приложение для внешних пользователей может требовать проверки Google, а в
  режиме Testing есть ограничения (число пользователей, срок refresh-токена). Это условия Google, их надо сверить в
  документации до выкладки. Я их не проверял.
- Не проверено на реальном Google и реальном кластере GKE: все тесты идут против фейкового эндпоинта токена.
- Device flow не используется: Google его не допускает для `cloud-platform`.
