# Область применения публичного OIDC-клиента веб-версии

**Status: ждёт ревью человеком**

## Проблема

Публичный client id веб-версии (настройка администратора, нужна для `browser-callback`) подставлялся в
`Descriptor.Params["web.client-id"]` для любого OIDC-кластера, а провайдер заменял им `client-id` из kubeconfig
(и сбрасывал client secret) для любого вида входа. Последствия, когда заданы `KUBRON_PUBLIC_URL` и клиент:

- `password`, `device-code` и `legacy-refresh` входили чужим клиентом, который у IdP может быть не настроен для этого
  вида входа;
- кластеры с другим IdP получали client id, неизвестный их провайдеру, и вход ломался вместо отката на
  `paste-redirect`;
- refresh-токен привязывался к веб-клиенту и после переключения терялся.

## Варианты

1. Настройка на каждый кластер (клиент в метаданных кластера). Точнее всего, но меняет метаданные кластера,
   оба хранилища, диалог кластера и API.
2. Одна настройка организации с привязкой к issuer и ограничением вида входа.
3. Оставить как было (отклонено: дефект).

## Решение

Вариант 2, минимальная замена существующей настройки:

- Настройка хранит пару `(clientId, issuerUrl)`. API: `GetWebOIDCClient`, `SetWebOIDCClient(clientId, issuerUrl)`;
  оба значения задаются вместе (или оба пусты), issuer только `https`, без запроса, фрагмента и данных пользователя.
- Приложение подставляет `web.client-id`, `web.redirect-url` и `web.issuer-url`, только если `grant` кластера
  `authcode` (или не указан) и issuer из kubeconfig совпадает с issuer настройки. Совпадение допускает различия
  регистра схемы и хоста, завершающие `/` и порт по умолчанию; всё остальное сравнивается точно, пустые значения
  не совпадают.
- Провайдер проверяет то же самое ещё раз (защита на случай ошибки в приложении): веб-клиент заменяет клиента
  только для `authcode` и только при совпадении `web.issuer-url` с издателем кластера.
- Запись прежнего вида (только client id) читается как «без issuer» и не применяется; публичное хранилище из
  `pkg/ext` с прежним интерфейсом (только client id) тоже читается без issuer, а сохранить в нём issuer нельзя
  (понятная ошибка). Отказ по умолчанию: лучше вход по `device-code` или `paste-redirect`, чем чужой клиент.

## Последствия

- После обновления администратор должен ввести issuer, иначе `browser-callback` не включится (вход работает через
  `device-code` и `paste-redirect`).
- Веб-клиент покрывает один IdP. Если нужен возврат на сервер для кластеров с разными IdP, потребуется клиент на
  каждый кластер (вариант 1), это отдельная задача.
- Refresh-токены, полученные через веб-клиент, привязаны к нему; при смене или удалении настройки пользователи
  входят заново.

## Отмена

Вернуть `GetWebOIDCClientID` и `SetWebOIDCClientID` и убрать проверки issuer и grant (возвращает исходный дефект).
