# ADR-0025: Kubron Lifecycle — оценка готовности и контроль изменений Kubernetes

- Статус: реализовано (2026-11-13)
- Дата: 2026-11-08
- Связано: ADR-0005, 0006, 0007, 0008, 0009, 0012, 0018, 0021, 0022, 0023, 0026, 0027; продуктовая концепция «Kubron Intelligence | Kubron Lifecycle», разделы 4 и 6

## Контекст

Эксплуатация Kubernetes включает регулярные изменения: обновление Kubernetes и системных компонентов, миграцию API, контроль конфигурационного дрейфа, резервное копирование и восстановление. Эти проверки могут быть распределены между инструментами и ручными процедурами.

Продуктовая концепция предлагает Kubron Lifecycle как отдельный модуль для оценки готовности к изменениям, обнаружения drift, проверки совместимости компонентов, фиксации истории и сопровождения maintenance workflows.

Для MVP настоящего ADR определены Upgrade Readiness Report, поиск deprecated/removed API, базовая проверка версий и статуса выбранных компонентов и экспортируемый отчёт. Drift detection концепция тоже включает, но он требует версионируемого baseline, нормализации по типам ресурсов и отдельного пользовательского процесса утверждения, поэтому вынесен в ADR-0027. Самостоятельное обновление control plane и cloud-managed компонентов в MVP не требуется.

Решение должно опираться на существующие подключения и tenant/access модель Kubron, не дублировать cluster manager и не выполнять скрытых изменений в пользовательских кластерах. Общие платформенные правила (доступ к кластеру, хранение в desktop и server, права, аудит, события, фоновые задачи) заданы в ADR-0026 и здесь не повторяются.

## Решение

### 1. Отдельный модуль оценки жизненного цикла

Kubron Lifecycle реализуется как отдельная функциональная область приложения. Для доступа к кластерам, сессионного контекста, авторизации, аудита, событий и хранения используются существующие механизмы Kubron (ADR-0005, 0007, 0009, 0012, 0018, 0022).

Все findings привязаны к конкретному кластеру и доступны только пользователям с правами на команду, которой принадлежит кластер. Проверки выполняются в пределах Kubernetes RBAC; read-only является режимом по умолчанию.

### 2. Upgrade Readiness — оценка, не выполнение обновления

Upgrade Readiness принимает выбранный кластер и целевую версию Kubernetes (если она указана), собирает доступную информацию и формирует отчёт: текущая версия Kubernetes; используемые API и обнаруженные deprecated/removed версии; версии и состояния выбранных системных компонентов; блокирующие проблемы; предупреждения и информационные findings; подготовительные действия и проверки после обновления.

Отчёт не является гарантией успешного обновления. Отсутствие данных о совместимости обозначается как «не проверено», а не как «совместимо».

Контракт отчёта содержит обязательное поле покрытия (`coverage`): какие источники реально проверены (живые объекты API, манифесты GitOps, локальные файлы), какие нет, режим проверки (общий Kubernetes или конкретный провайдер), версии и даты используемых матриц. Отчёт без заполненного `coverage` невалиден. Так «не проверено» становится частью структуры данных, а не только текста.

В MVP Kubron не запускает upgrade control plane, node groups или cloud-managed компонентов. Поддержка конкретного провайдера и целевых версий должна быть явной; общая Kubernetes-проверка не должна выдаваться за полную проверку EKS/GKE/AKS.

### 3. API Compatibility

Анализатор ищет использование устаревших и удалённых Kubernetes API в доступных манифестах и данных кластера.

Каждый finding содержит идентификатор ресурса, если он может быть установлен, обнаруженные apiVersion и kind, характер проблемы (deprecated или removed для целевой версии), источник данных и рекомендацию по миграции.

Покрытие зависит от доступных источников. Если Kubron не видит исходные манифесты GitOps или иные декларативные файлы, отчёт явно указывает ограничение. Нельзя заявлять, что проверены все манифесты, если анализировались только живые объекты API.

Матрица deprecated/removed API генерируется из данных апстрима Kubernetes (deprecation guide и справочник API) скриптом при сборке, встраивается в поставку и версионируется; в отчёте видны её версия и дата. Сеть во время проверки не нужна. Окно поддерживаемых целевых версий фиксируется при реализации и покрывается тестовыми фикстурами.

### 4. Component Compatibility

Первая версия проверяет ограниченный каталог выбранных системных компонентов, add-ons и операторов. Результат содержит обнаруженную версию, состояние, целевую версию Kubernetes и статус проверки совместимости.

Статусы различают: совместимость подтверждена доступным источником; обнаружено известное ограничение; данных недостаточно; компонент не распознан.

Источник и дата актуальности матрицы совместимости видны в отчёте. Неизвестная комбинация версий не считается автоматически совместимой.

### 5. Configuration Drift Detection — вынесено в ADR-0027

Обнаружение дрейфа конфигурации в состав этого ADR и его MVP не входит. Решение о baseline, нормализации, исключениях, утверждении эталона и хранении истории drift принимается в ADR-0027. До его принятия Lifecycle не сохраняет baseline и не сообщает о drift.

### 6. История readiness-проверок

Результаты проверок хранятся через `Store` (ADR-0007) по контракту ADR-0026: в desktop и в server с одной семантикой, с привязкой к кластеру и tenant scope (ADR-0012). Запись содержит кластер, целевую версию, время, инициатора, findings со статусами, `coverage` и версии использованных матриц. История нужна, чтобы сравнивать отчёты во времени и показывать, что изменилось с прошлой проверки.

Стартовые значения retention: до 50 отчётов на кластер и не дольше 180 дней; настраивается организацией (server) или приложением (desktop). Значения фиксируются при реализации.

Данные отчётов не содержат значения Secret или иные чувствительные значения. Применяются правила редакции чувствительных данных ADR-0022. Экспортируемый отчёт включает раздел `coverage`, чтобы читатель видел, что не проверено.

### 7. Интеграции и provider-specific capabilities

Общие проверки Kubernetes отделяются от provider-specific проверок. Возможности EKS, GKE, AKS и self-managed кластеров не считаются одинаковыми.

В MVP приоритет — проверки, которые можно выполнить через Kubernetes API и доступные данные Kubron. Провайдеро-специфичные API, автоматическое обновление и дополнительные cloud permissions не добавляются без отдельной проверки и описания capability.

Интеграции GitOps, backup/recovery и compliance-профили остаются направлениями развития. ADR-0023 уже описывает чтение и действия Flux рядом с Argo CD; Lifecycle может использовать доступные GitOps-данные, но не должен повторно реализовывать GitOps-контроллеры или подменять их reconcile-модель.

### 8. Изменяющие операции — вне MVP

MVP только оценивает состояние и формирует рекомендации. Он не выполняет upgrade и ничего не меняет в кластере.

Будущие maintenance workflows и remediation должны иметь preview, описание последствий, отдельное право, подтверждение уполномоченного пользователя, audit log и post-check. Автоматическое исправление по умолчанию выключено.

## Объём MVP

Входит:

1. Upgrade Readiness Report для выбранного кластера.
2. Обнаружение версии Kubernetes и доступных сведений о системных компонентах.
3. Поиск deprecated/removed Kubernetes API в пределах явно обозначенных источников.
4. Базовая проверка версий и состояния выбранных компонентов.
5. История readiness-проверок в desktop и server.
6. Экспортируемый отчёт с приоритетами, объяснениями, рекомендуемыми действиями и разделом `coverage`.

Не входит:

- запуск обновления Kubernetes или cloud-managed компонентов;
- обнаружение и исправление drift, baseline (ADR-0027);
- полноценная интеграция со всеми GitOps-системами;
- backup execution и восстановление;
- полный compliance framework;
- календарь обслуживания и автоматические maintenance workflows;
- гарантия совместимости всех комбинаций версий и провайдеров.

## Рассмотренные альтернативы

- **Автоматически выполнять upgrade в первом релизе.** Отклонено: провайдеры имеют разные ограничения, а ошибка может повлиять на production. Сначала вводится readiness assessment; выполнение потребует отдельного ADR.
- **Включить drift detection в MVP этого ADR.** Не выбрано: требует версионируемого baseline, нормализации по каждому типу ресурса и процесса утверждения; это самостоятельное решение с собственными рисками (ADR-0027). Readiness можно выпустить и без него.
- **Один универсальный алгоритм совместимости для всех провайдеров.** Отклонено: cloud-managed компоненты и процедуры обновления отличаются. Общими остаются только проверки, подтверждённые Kubernetes API и известными источниками данных.
- **Отдельная система хранения и подключения кластера.** Отклонено: дублирует Store, cluster manager и tenant/access модель Kubron.

## Последствия

- Первый релиз даёт оценку рисков без доступа на запись и без выполнения опасных операций.
- Точность отчёта зависит от полноты инвентаризации, исходных манифестов и актуальности матриц совместимости; непроверенные области должны быть видны пользователю.
- История readiness-проверок требует новых методов в `Store`, файловой и PostgreSQL реализаций, миграции и контрактных тестов (ADR-0026).
- Встроенная матрица deprecated/removed API требует скрипта генерации и обновления при выходе новых версий Kubernetes; устаревшая матрица видна в отчёте по дате.
- Интеграции с GitOps и backup/recovery расширят покрытие, но не являются обязательными зависимостями MVP.
- Автоматическое исправление и upgrade остаются отдельными архитектурными решениями с более строгими правами и подтверждением.

## Решено при согласовании (2026-11-08)

- Drift detection вынесен в ADR-0027; MVP этого ADR — readiness без baseline.
- История readiness-проверок хранится в desktop и в server; retention по умолчанию до 50 отчётов на кластер и не дольше 180 дней.
- Матрица deprecated/removed API встраивается в поставку и генерируется из данных апстрима Kubernetes.
- Целевые версии: три последние минорные версии Kubernetes, поддерживаемые апстримом на момент выпуска Kubron; окно обновляется с релизами и записывается в отчёт.
- Источники манифестов в MVP: только живые объекты API. Манифесты Argo CD, Flux и Git не анализируются, и отчёт прямо сообщает об этом в `coverage`. Расширение источников — отдельное решение.
- Матрица совместимости add-ons и операторов: каталог в репозитории с ограниченным списком компонентов; для каждой записи указаны ссылка на официальную документацию совместимости проекта и дата проверки. Компоненты вне каталога получают статус «не распознан».
- Provider-specific проверки в первом релизе отсутствуют: выполняются только проверки через Kubernetes API, и отчёт указывает режим «общий Kubernetes».

Открытых вопросов нет. Решение принято тимлидом и реализовано (2026-11-13).
