# ADR-0059: Универсальный OIDC-вход и ядро SSO

- Статус: In Progress
- Дата: 2026-11-28
- Область: authentication / identity
- Связано: ADR-0004, ADR-0007, ADR-0011, ADR-0016, ADR-0018; промпт `docs/prompts/sso/01-adr-and-sso-core.md`

## Контекст

ADR-0011 определил стандартный OIDC за интерфейсом аутентификации, но не описал полноценный поток входа, безопасное состояние callback и политику сопоставления внешней идентичности с пользователем Kubron. Реализация должна работать с любым совместимым OIDC-провайдером, не зависеть от HTTP-оболочки и хранилища пользователей и не добавлять зависимость от PostgreSQL. Одновременно все сетевые обращения к IdP обязаны соблюдать SSRF/TLS-политику ADR-0018.

## Решение

1. **Протокол.** Использовать OpenID Connect Authorization Code Flow с PKCE S256. Каждый вход генерирует криптографически случайные `state`, `nonce` и PKCE verifier. Callback сверяет `state` сравнением постоянного времени; обмен кода выполняется с исходным verifier и точным redirect URI. ID-токен проверяется через `coreos/go-oidc`: подпись по JWKS, issuer, audience и expiration; claim `nonce` сравнивается с сохранённым значением. Если callback содержит `iss` (RFC 9207), он обязан совпасть с настроенным issuer.

2. **Независимость от поставщика.** Один IdP на установку, неизвестный заранее. Настройки discovery берутся из стандартного OIDC discovery. Продукт не содержит специальных веток или обязательных расширений для Keycloak, Authentik, Azure AD либо другого поставщика.

3. **Сетевая политика.** Discovery и token/JWKS запросы выполняются только HTTP-клиентом `internal/idpnet`, переданным в `oidc.ClientContext`. В серверном режиме issuer должен быть HTTPS. HTTP и loopback разрешаются только desktop-режиму. Для провайдера может быть указан PEM-файл корневого CA. Повторные попытки discovery выполняются при следующем запросе после ошибки; ошибка IdP не блокирует запуск приложения и не кэшируется как успешная инициализация.

4. **Внешняя идентичность.** Канонический ключ — пара `(issuer, sub)`. Имя пользователя извлекается из настроенного claim (по умолчанию `preferred_username`); если значение отсутствует или недопустимо, используется local-part claim `email`. Результат обрезается по краям и обязан соответствовать `auth.ValidateUsername` (3–32 символа, латиница, цифры, точка, дефис, подчёркивание). Имя и email — атрибуты, но не идентификаторы для автоматического объединения учётных записей. Привязка существующего локального пользователя допускается только при явном `KUBRON_OIDC_LINK_EXISTING=1`; по умолчанию выключена. Пока не создан первый локальный пользователь, SSO-вход запрещён: первый администратор создаётся обычной первичной настройкой.

5. **Создание и роли.** `KUBRON_OIDC_AUTO_CREATE` включает автоматическое создание пользователя (по умолчанию включено). Группы берутся из claim `groups` (настраиваемый `KUBRON_OIDC_GROUPS_CLAIM`). Совпадение с `KUBRON_OIDC_ADMIN_GROUPS` назначает `admin`, затем проверяются `KUBRON_OIDC_OPERATOR_GROUPS` для `operator`; иначе применяется известная роль `KUBRON_OIDC_DEFAULT_ROLE` (по умолчанию `user`). При настроенном сопоставлении групп IdP является источником истины для роли при каждом входе. Понижение последнего активного администратора запрещено; это ограничение реализуется на уровне auth-сервиса.

6. **Локальный вход.** `KUBRON_OIDC_DISABLE_LOCAL_LOGIN=1` отключает парольный вход на сервере. Для аварийного доступа администратор удаляет переменную и перезапускает сервер. Кнопка входа может получить подпись из `KUBRON_OIDC_BUTTON_LABEL`.

7. **Состояние callback без БД.** `state`, `nonce`, PKCE verifier, redirect URI и время создания объединяются в `FlowState` и шифруются AES-256-GCM. Ключ выводится через HKDF-SHA256 из `KUBRON_SECRET_KEY` с отдельной доменной меткой `kubron/oidc/sign-in-flow/v1`. Контейнер аутентифицирован, версия формата проверяется, срок жизни — 10 минут. Если мастер-ключ не задан, используется случайный ключ процесса. Этот fallback пригоден только для одной реплики и теряет возможность завершить уже начатый вход после перезапуска процесса; для нескольких реплик обязателен общий стабильный `KUBRON_SECRET_KEY`. Состояние не хранится в PostgreSQL.

8. **Границы ядра.** Пакет `internal/sso` отвечает только за конфигурацию, OIDC discovery, начало/завершение протокола, проверку токена, извлечение Identity, шифрование FlowState и отображение групп в роль. Он не знает о HTTP-маршрутах, cookie, сессиях, таблицах пользователей или транзакциях хранилища. Их интеграция выполняется последующими этапами.

## Рассмотренные альтернативы

- **Жёсткая привязка к Keycloak.** Отвергнута: IdP заранее неизвестен, а OIDC discovery даёт совместимость с любым стандартным провайдером.
- **SAML.** Отвергнут для текущей задачи: OIDC уже принят в ADR-0011 и покрывает целевые провайдеры с меньшей сложностью интеграции.
- **Автоматическая привязка по email или имени.** Отвергнута: атрибуты могут меняться, повторяться или не быть подтверждёнными; это создаёт риск захвата существующей локальной учётной записи.
- **Хранение состояния входа в БД.** Отвергнуто: создаёт лишнюю зависимость от PostgreSQL и не подходит для файлового/desktop-режима. Зашифрованный переносимый контейнер позволяет любой реплике обработать callback при общем мастер-ключе.

## Последствия

- OIDC-ядро не требует PostgreSQL и может использоваться как серверной, так и desktop-оболочкой; desktop-режим дополнительно допускает loopback HTTP для локального callback.
- Все реплики должны иметь одинаковый `KUBRON_SECRET_KEY`, иначе callback, начатый на одной реплике, не будет расшифрован другой.
- Без `KUBRON_SECRET_KEY` используется эфемерный ключ процесса: допустима только одна реплика, а перезапуск аннулирует незавершённые потоки входа.
- Client secret читается только из окружения и не включается в FlowState, Identity, сообщения ошибок или журнал. Коды авторизации и токены не включаются в ошибки.
- ADR-0011 остаётся неизменным и реализуется этим решением; изменения пользовательских записей и запрет понижения последнего администратора относятся к следующему этапу интеграции auth/storage.
- Для полноценного SSO остаются отдельные этапы: привязка `(issuer, sub)` к пользователю и первому администратору, HTTP callback/session, frontend и desktop UX.
