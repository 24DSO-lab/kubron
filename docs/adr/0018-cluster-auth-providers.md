# ADR-0018: Способы входа в кластер: провайдеры учётных данных и вызовы (challenge)

- Статус: принято
- Дата: 2026-11-02
- Связано: ADR-0002, 0003, 0005, 0006 (частично заменяет), 0008, 0015; задача 3.7; тикеты `docs/tickets/cluster-auth.md`;
  журнал решений `docs/decisions/2026-11-02-cluster-auth.md`

## Контекст

Задача 3.7 решила подключение к кластеру для веба узко: kubeconfig со статическими данными, `in-cluster` и `oidc-password`.
Всё остальное в вебе отвергается ошибкой (`ErrOIDCAuthCode`, `ErrExecForbidden`), а `oidc-password` требует PostgreSQL.
Это не годится для продукта «для всех»: пользователь вставляет kubeconfig и ожидает, что Kubron сам поймёт, как войти,
и спросит только то, чего не хватает. Требования:

1. Одно поведение в десктопе и в вебе: пользователь не выбирает вид подключения.
2. Поддержаны все распространённые способы входа: токен, сертификат, `oidc-login` (password, authcode, device-code),
   `auth-provider: oidc`, облачные плагины (EKS, GKE, AKS и др.), прочие `exec`.
3. Безопасность важнее удобства: на сервере нельзя выполнять произвольные команды из загруженного kubeconfig (RCE).
4. Для интерактивных входов учётные данные личные: у пользователя свои права в кластере (решение владельца продукта, 2026-11-02).

## Решение

### 1. Провайдеры учётных данных

Разбор kubeconfig и получение токена выделяются в интерфейс `credential.Provider`:

- `Detect(kubeconfig, context) -> Descriptor`: чистая функция без сетевых и файловых побочных эффектов; определяет вид входа и его
  несекретные параметры (издатель, client id, grant, scopes, команда `exec`). Заменяет `ClassifyAuth`.
- `Begin(ctx, subject) -> Token | Challenge`: пытается получить токен из сохранённых данных (refresh, кэш); если данных нет или
  они недействительны, возвращает **вызов**, а не ошибку.
- `Continue(ctx, challenge, answer) -> Token | Challenge`: продолжает вход (ответ пользователя или завершение во внешнем браузере).
- Токен подставляется в `rest.Config` через `WrapTransport`; exec-блок в `rest.Config` не попадает никогда.

Провайдеры регистрируются в реестре; сторонние добавляются через `pkg/ext` (ADR-0011).

### 2. Вызов (`AuthChallenge`) вместо строки ошибки

Бэкенд возвращает структуру, а интерфейс рисует один универсальный диалог по её виду. Выбор способа входа делает Kubron, а не пользователь.

| Вид вызова | Что видит пользователь | Где |
| --- | --- | --- |
| `credentials` | поля логин и пароль | везде |
| `device-code` | код и ссылка, ожидание подтверждения (RFC 8628) | везде |
| `browser-loopback` | открывается браузер, вход завершается сам (RFC 8252, `127.0.0.1`, случайный порт или порт из kubeconfig) | десктоп |
| `browser-callback` | вход по ссылке, возврат на `https://<kubron>/…/callback` | веб, если для кластера задан веб-клиент |
| `paste-redirect` | вход по ссылке и вставка адреса, на который перешёл браузер (redirect из kubeconfig, например `http://localhost:8000`) | веб, запасной путь без изменений в IdP |
| `secret-fields` | поля, нужные провайдеру (например, ключи AWS) | везде |
| `manual-token` | показана точная команда из kubeconfig, которую пользователь запускает у себя, и поле для вставки результата | веб, для любого неподдержанного `exec` |
| `confirm-exec` | команда, аргументы и окружение; подтверждение запуска | десктоп |

Порядок выбора в вебе: `device-code` (если IdP объявляет его в discovery) → `browser-callback` (если админ настроил веб-клиент) →
`paste-redirect`; при отказе IdP (`unauthorized_client` и т. п.) происходит автоматический откат к следующему способу.
`manual-token` — последний запасной вариант для любого `exec` без нативного провайдера.

Состояние вызова: непредсказуемый id, срок жизни до 10 минут, одноразовое завершение, привязка к веб-сессии и пользователю;
в режиме нескольких реплик хранится в PostgreSQL (callback может прийти на другую реплику).

### 3. Чьи учётные данные

- Область (`scope`) учётных данных: `user` или `team`.
- Статические данные из kubeconfig (токен, сертификат, basic) — `team`, как сейчас.
- Интерактивные виды (authcode, device-code, password, облачные плагины) — `user`: у каждого участника свои права в кластере.
  Итоговый доступ — пересечение прав в приложении (app-RBAC) и прав пользователя в Kubernetes.
- Для `oidc-password` админ команды может явно выбрать «общая техническая учётная запись» (`team`): так продолжают работать
  кластеры, подключённые по задаче 3.7. Данные переносятся миграцией без изменения поведения.
- **Пароль личной учётной записи не сохраняется.** Хранится только refresh-токен (зашифрованный). Когда он перестал действовать,
  пользователь получает новый вызов. Пароль сохраняется только для `team`-области.
- Кластер остаётся собственностью команды: админ добавляет описание (адрес, CA, вид входа), каждый участник входит сам при первом подключении.
- Фоновая проверка состояния (3.6) для кластеров с `user`-областью проверяет только доступность адреса и TLS; состояние
  «нужен вход» отличается в интерфейсе от «недоступен».

### 4. Пул подключений и единая точка получения конфигурации

Ключ общего пула (ADR-0005) становится `(кластер, субъект)`: informer, запущенный с правами одного пользователя, не должен
отдавать данные другому. Для `team`-области ключ не меняется. Все потребители (ресурсы, Helm, терминал, логи, port-forward,
метрики) получают `rest.Config` только через одну функцию `ConfigFor(session, cluster)`; статический тест запрещает строить конфиг в обход.

### 5. `exec`

- **Веб:** произвольный `exec` из загруженного kubeconfig не выполняется никогда, никакой настройкой. Вместо него: нативные
  провайдеры (oidc-login, затем EKS, GKE, AKS, далее по каталогу) и запасной `manual-token` для всего остального.
  Песочница с allowlist отклонена владельцем продукта (2026-11-02).
- **Десктоп:** `exec` выполняется по спецификации `client.authentication.k8s.io` (v1, v1beta1: `interactiveMode`, `provideClusterInfo`, `env`,
  кэш по `expirationTimestamp`), но **только после подтверждения** (`confirm-exec`): команда, аргументы и окружение показываются пользователю,
  решение запоминается по хэшу всего блока. Любое изменение блока требует нового подтверждения. Это защита от kubeconfig из недоверенного источника.
  Порядок (решение владельца, 2026-11-02): если плагин найден в `PATH`, запускается он (общий кэш и состояние входа с `kubectl`);
  если не найден, используется нативный провайдер, а при его отсутствии показывается `installHint`.

### 6. Хранение секретов

Envelope-шифрование (ADR-0008): ключ данных шифрует секреты, мастер-ключ защищает ключ данных.

- Десктоп: мастер-ключ в системном хранилище (Keychain, Credential Manager, Secret Service) через `zalando/go-keyring`. Если оно недоступно (безголовый Linux), файл `0600`
  с явным предупреждением в интерфейсе.
- Веб с PostgreSQL: `KUBRON_SECRET_KEY` обязателен (как сейчас).
- Веб без PostgreSQL (личный режим): `KUBRON_SECRET_KEY`, а если не задан, ключ создаётся один раз в каталоге данных (`0600`) с записью в журнал и
  предупреждением в документации. Это снимает ограничение «нужен PostgreSQL».
- Данные в хранилище: `cluster_credentials` (кластер, владелец, вид, `secret_enc`, `secret_key_id`, срок, субъект для аудита, `version`).
  `kubron-server rekey` покрывает и их.

### 7. Безопасность входа

- OIDC: PKCE (S256), `state`, `nonce`, проверка подписи и `iss`/`aud` ID-токена (`coreos/go-oidc`), защита от mix-up (RFC 9207), точное сравнение redirect URI.
- Адреса IdP в вебе проходят SSRF-политику. Для `oidc-password` она уже действует (`netpolicy.ScopeClusterAPI`, включая `token_endpoint`
  из ответа IdP, см. `docs/deploy.md`); решение распространяет её на все новые обращения сервера: discovery, authorization и token,
  device, JWKS, userinfo, отзыв токена и эндпоинты облачных провайдеров. Только https, повторная проверка редиректов, лимиты
  размера и времени. Исключение для `http` и loopback только в десктопе.
- Ограничения попыток ввода учётных данных на пользователя и на IdP: Kubron не должен стать средством подбора паролей.
- Обновление refresh-токена: один обновляющий на субъект (`singleflight` в реплике, оптимистичная блокировка по `version` между репликами);
  ротация refresh-токенов не должна приводить к отзыву сессии из-за гонки. `invalid_grant` означает новый вызов, а не ошибку.
- Секреты не попадают в API, события, журнал, логи и метрики; это проверяется тестом с контрольной строкой.
- Параметры kubeconfig, ослабляющие защиту (`insecure-skip-tls-verify` у IdP, пути к файлам сервера, `proxy-url`), в вебе отклоняются; встроенные `-data` поля принимаются.
- Аудит: начало и завершение входа, неудача, отзыв; субъект Kubernetes (claim `sub`/логин) записывается рядом с пользователем приложения.
- Отзыв: исключение из команды, удаление пользователя, смена пароля, выход и кнопка «отключиться от кластера» удаляют личные данные, закрывают его терминалы,
  логи и port-forward (механизм `EnforceAccess` расширяется).

## Рассмотренные альтернативы

- **Один общий вход для команды (как в ADR-0006).** Проще, но права всей команды равны правам одной учётной записи, а браузерный вход по природе личный.
  Оставлен для статических данных и по явному выбору для `oidc-password`.
- **Impersonation или проброс токена приложения.** Требует изменений в каждом кластере; не подходит для «любого кластера в мире».
- **Запуск `kubectl`/плагинов на сервере, в том числе в песочнице с allowlist админа.** RCE или большая поверхность атаки и нет
  терминала для интерактивного ввода. Отвергнуто владельцем продукта.
- **Только `manual-token` для всего интерактивного.** Работает везде, но заставляет пользователя выполнять команды; оставлено как запасной вариант.
- **Хранить пароль пользователя для повторного входа.** Удобнее, но каждая утечка БД раскрывает реальные пароли; отвергнуто для `user`-области.

## Последствия

- Права пользователя в кластере больше не совпадают с правами команды: два участника одной команды могут видеть разное. Это ожидаемо и безопаснее.
- Количество informers растёт с числом пользователей одного кластера; действуют TTL простоя и бюджет LIST (2.8). Нужен нагрузочный тест.
- Меняется контракт `ConnectToCluster` (результат с вызовом вместо ошибки) и добавляются `AnswerChallenge`/`PollChallenge`; Wails-привязки и веб-клиент обновляются вместе.
- ADR-0006: пункт «проброс личной идентичности вне плана» заменён этим решением для интерактивных видов входа; остальное сохраняется.
- Новые зависимости: `coreos/go-oidc`, `golang.org/x/oauth2`, `zalando/go-keyring` (выбор и причины — в `docs/decisions/2026-11-02-cluster-auth.md`), SDK подписи AWS (в B.7a).
- Каждый новый облачный провайдер добавляется независимо и не меняет интерфейс.
