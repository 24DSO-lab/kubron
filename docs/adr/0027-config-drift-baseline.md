# ADR-0027: Обнаружение дрейфа конфигурации и baseline

- Статус: предложено
- Дата: 2026-11-08
- Связано: ADR-0006, 0007, 0008, 0012, 0022, 0023, 0025, 0026; выделено из ADR-0025 (раздел 5)

## Контекст

Продуктовая концепция Kubron Lifecycle включает обнаружение дрейфа конфигурации: отличий наблюдаемого состояния ресурса от ожидаемого. ADR-0025 выделил из своего MVP Upgrade Readiness, а дрейф вынес сюда, потому что это не «сравнение двух YAML», а самостоятельная подсистема с собственными рисками:

- живые объекты Kubernetes непрерывно меняются без участия человека: контроллеры обновляют `status` и `managedFields`, admission-механизмы и defaulting добавляют поля, HPA меняет `replicas`, Deployment-контроллер пишет аннотации ревизий. Наивное сравнение порождает шум, и пользователи перестают доверять результату;
- эталон (baseline) должен откуда-то взяться. Если брать текущее состояние автоматически, можно закрепить уже существующий дрейф;
- спецификации содержат чувствительные значения (literal-значения env, данные ConfigMap), которые нельзя сохранять в истории открытым текстом;
- факт отличия не доказывает, кто его внёс;
- baseline и история должны работать в desktop и в server (ADR-0026) и не зависеть от реплики.

Общие платформенные правила (доступ к кластеру, хранение, права, аудит, события, фоновые задачи) заданы в ADR-0026 и здесь не повторяются.

## Решение

### 1. Принципы

Дрейф определяется как различие между нормализованным наблюдаемым состоянием ресурса и явно заданной версией baseline. Модуль только читает кластер: он не применяет baseline к кластеру и не исправляет отличия. Baseline — данные Kubron, а не объект кластера; в пользовательский кластер ничего не устанавливается и не записывается.

### 2. Модель baseline

- Baseline принадлежит кластеру и команде этого кластера (ADR-0012). Он описывает область (namespace и/или селектор) и набор ресурсов (group/version/kind, namespace, name).
- Baseline состоит из **неизменяемых версий**. Версия содержит идентификатор, нормализованные объекты, версию правил нормализации, источник, автора, время и комментарий. «Обновление» baseline создаёт новую версию; предыдущие сохраняются, одна версия помечена активной.
- **Источник версии в MVP — снимок живого состояния** (`live-snapshot`), выполненный по явному действию пользователя. Автоматическое создание или молчаливое обновление baseline запрещено.
- Перед созданием версии пользователь видит preview: какие ресурсы и поля будут зафиксированы и, если есть предыдущая версия, чем снимок отличается от неё. Интерфейс прямо сообщает, что фиксируется текущее состояние как эталон, включая возможные уже существующие отклонения.
- Создание версии, смена активной версии, добавление исключений и удаление baseline требуют права `baseline.manage` (ADR-0026, раздел 5) в команде-владельце кластера и записываются в аудит. Подтверждения вторым человеком не требуется, в том числе для кластеров с тегом `prod`: достаточно одного пользователя с этим правом, а защиту обеспечивают preview, неизменяемые версии и аудит.
- GitOps desired state (Argo CD, ADR-0023) остаётся перспективным источником baseline, но не входит в MVP: для корректного сравнения он требует учёта defaulting на стороне API-сервера (например, server-side dry-run), что является отдельным решением.

### 3. Нормализация и исключения

Сравниваются нормализованные объекты: `spec` и выбранные части `metadata` (`labels`, `annotations`). Всегда исключаются поля, которые меняются автоматически: `status`, `metadata.managedFields`, `resourceVersion`, `uid`, `generation`, `creationTimestamp`, `selfLink`, аннотация `kubectl.kubernetes.io/last-applied-configuration`, служебные аннотации контроллеров (например, ревизии Deployment).

Для каждого поддерживаемого типа ресурса есть версионируемое правило нормализации: дополнительные исключения, обработка defaulted-полей, упорядочивание списков. Например, `spec.replicas` исключается для Deployment и StatefulSet, на которые указывает HPA. Правила покрываются тестами на фикстурах реальных объектов. Версия правил записывается в baseline и в результат сравнения; сравнение версий правил разных поколений не выполняется молча.

Пользовательские исключения («игнорировать путь P для ресурса R» или «для типа T в namespace N») хранятся в версии baseline, требуют `baseline.manage`, комментария и могут иметь срок действия. Применённые исключения видны в результате сравнения.

### 4. Поддерживаемые ресурсы и чувствительные значения

Список типов MVP ограничен и расширяется добавлением правила нормализации: Deployment, StatefulSet, DaemonSet, Service, Ingress, NetworkPolicy, ConfigMap.

**Secret не поддерживается и не читается.** Для остальных типов:

- значения, способные нести секрет, — literal-значения `env[].value` и данные ConfigMap — не сохраняются и не показываются открытым текстом. В baseline и в истории хранится keyed hash значения: HMAC-SHA256, где ключом служит случайная соль, созданная для каждой версии baseline и хранящаяся вместе с ней в зашифрованном виде. Проверка считает hash живого значения с солью той версии, с которой сравнивает. Поэтому результат не зависит от ротации ключа keyring: `Rekey` перешифровывает версию вместе с солью, а hash остаются сравнимыми. Diff сообщает «значение ключа K изменено, добавлено или удалено» без содержимого;
- остальные текстовые поля (аннотации и т. п.) проходят редакцию по ADR-0022;
- в server версии baseline дополнительно шифруются как чувствительные данные хранилища (ADR-0008); таблицы baseline входят в `Rekey` и проверку ключей при старте.

### 5. Проверка и результат

Проверка выполняется по запросу пользователя, она короткая и синхронная (ADR-0026, раздел 8) и требует права `read`. Для каждого ресурса baseline результат — один из статусов:

- «соответствует»;
- «изменён» (список изменённых путей с нормализованным старым и новым значением, с учётом раздела 4);
- «отсутствует в кластере»;
- «не проверено» (нет прав Kubernetes, ошибка API, тип недоступен) — отдельно от «соответствует»;
- «новый ресурс вне baseline» — режим выключен и в MVP не реализуется; добавляется позже без изменения контракта статусов.

Результат содержит кластер, версию baseline, версию правил нормализации, применённые исключения, число проверенных и пропущенных ресурсов с причинами, время и инициатора. Частичная недоступность не превращается в пустой успех.

Приоритет изменения определяется правилами типа, а не AI: например, изменение `image`, `resources` или `securityContext` выше, чем изменение `labels`.

### 6. Источник изменения

Источник изменения указывается только при наличии доказательства и всегда с названием источника: запись аудита Kubron о применении YAML этим приложением; поле `managedFields`, показывающее последнего менеджера поля и время (например, `kubectl` или контроллер GitOps), с пометкой «по данным managedFields». Менеджер поля не приписывается конкретному пользователю. Само отличие не доказывает, кто его внёс.

### 7. История

Версии baseline, результаты проверок и исключения хранятся через `Store` (ADR-0007) по контракту ADR-0026: в desktop и server с одной семантикой, с tenant scope (организация, команда, кластер). Стартовые значения retention: результаты проверок 90 дней; версии baseline хранятся до явного удаления, но не менее 20 последних версий на baseline. Значения настраиваются организацией (server) или приложением (desktop) и фиксируются при реализации. Удаление по retention выполняет задача на `internal/jobs`.

### 8. Аудит и права

В аудит пишутся: создание версии, смена активной версии, добавление и удаление исключения, удаление baseline. Запись содержит субъект, кластер, идентификатор baseline и версии, число ресурсов, комментарий, но не содержимое объектов. Запуск проверки пишется в технический журнал с correlation ID, как прочие операции чтения (ADR-0022, ADR-0026).

### 9. Вне решения

Автоматическое исправление дрейфа и применение baseline к кластеру; периодические и фоновые проверки с уведомлениями; GitOps-источник baseline; baseline из нескольких кластеров и сравнение кластеров между собой; compliance-политики. Каждое из направлений требует отдельного решения.

## Объём MVP

Входит:

1. Baseline как набор неизменяемых версий из снимка живого состояния с preview и аудитом.
2. Нормализация и сравнение для ограниченного набора типов ресурсов.
3. Результат проверки с явными статусами, включая «не проверено».
4. Пользовательские исключения с комментарием и сроком.
5. Защита чувствительных значений (keyed hash, шифрование в server, редакция).
6. История версий и результатов в desktop и server.

Не входит: всё из раздела 9.

## Рассмотренные альтернативы

- **Drift только через GitOps.** Не выбрано для MVP: не каждый кластер подключён к GitOps, а сравнение desired и live требует учёта defaulting. GitOps остаётся предпочтительным будущим источником.
- **Автоматически считать текущее live-состояние baseline.** Отклонено: закрепляет уже существующий дрейф. Создание и принятие baseline — явные и аудируемые.
- **Сравнивать сырые YAML.** Отклонено: шум от полей, которые меняют контроллеры и API-сервер, делает результат бесполезным.
- **Сравнивать только allowlist полей по типу.** Надёжнее против шума, но пропускает неожиданные изменения. Выбран подход «нормализованный `spec` за вычетом исключений»: изменения не теряются, а шум управляется правилами и пользовательскими исключениями.
- **Хранить значения env и ConfigMap открытым текстом.** Отклонено: в них регулярно оказываются секреты.
- **Server-side dry-run для сравнения с манифестами.** Перспективно для GitOps-источника; требует права на dry-run `patch`/`create` и отдельного решения, в MVP не используется.

## Последствия

- Дрейф даёт полезный сигнал только при поддержке правил нормализации по типам: это постоянная работа при выходе новых версий Kubernetes и CRD.
- Сравнение по keyed hash не показывает, на что именно изменилось значение; это сознательная цена безопасности. Соль у каждой версии своя, поэтому hash одного значения в разных версиях различаются: две уже сохранённые версии нельзя сравнить по значениям ConfigMap и env. Preview при создании новой версии этого не требует: он сравнивает живые значения с предыдущей версией, считая их hash с её солью.
- Baseline, привязанный к снимку, фиксирует состояние на момент снимка, а не «правильное» состояние; интерфейс обязан это объяснять.
- Хранение baseline и истории требует новых методов в `Store`, файловой и PostgreSQL реализаций, миграций, контрактных тестов, учёта в `Rekey` и новой таблицы прав (ADR-0026).
- Право `baseline.manage` меняет таблицу ролей и требует записи в CHANGELOG.

## Решено при согласовании (2026-11-08)

- Состав типов ресурсов MVP: Deployment, StatefulSet, DaemonSet, Service, Ingress, NetworkPolicy, ConfigMap.
- Подтверждение вторым человеком не требуется.
- Режим «новые ресурсы вне baseline» в MVP не реализуется.
- Hash значений считаются HMAC-SHA256 с солью каждой версии baseline; зависимости от ротации ключа keyring нет.
- Периодические проверки в первый релиз не входят; проверка выполняется по запросу пользователя.
- Retention: результаты проверок 90 дней; версии baseline до явного удаления, но не менее 20 последних.

Открытых вопросов нет. Статус остаётся «предложено» до принятия решения тимлидом.
