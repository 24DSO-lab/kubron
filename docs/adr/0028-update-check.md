# ADR-0028: Проверка обновлений и способ установки

- Статус: реализовано (2026-11-13)
- Дата: 2026-11-09
- Связано: ADR-0003, 0010, 0015, 0021

## Контекст

Kubron выходит в двух оболочках (десктоп на Wails и веб-сервер), а веб-сервер ставят по-разному: чартом Helm, манифестами или
GitOps, контейнером вне Kubernetes, бинарником. Пользователю нужно узнать, что вышла новая версия, и понять, что именно ему
делать. Одной кнопки «Обновить» нет, и она была бы вредна:

- сервер в контейнере не должен менять собственный образ: у него нет на это прав, а образ неизменяем по замыслу;
- подмена исполняемого файла десктопа без проверки подписи — риск цепочки поставки (ADR-0021);
- команда обновления зависит от способа установки (`helm upgrade` для релиза в своём пространстве имён, `docker pull`,
  `apt install ./kubron_….deb`), и неверная команда хуже, чем её отсутствие.

Кроме того, сервер часто работает в закрытых сетях, где исходящие запросы на GitHub запрещены политикой.

## Решение

### 1. Только сообщаем, ничего не устанавливаем

Пакет `internal/update` определяет версию, наличие новой версии и способ установки и возвращает ссылку на релиз, файл для
скачивания (десктоп) или готовые команды (веб, `.deb`). Установку выполняет человек или его система развёртывания.

### 2. Источник версии и сравнение

- Версия сборки — `main.version`, её задаёт `-ldflags "-X main.version=<версия>"` (Dockerfile для сервера, `release.yml` для
  десктопа). Без флага остаётся `dev`: проверка отключена, потому что сравнивать не с чем.
- Единственный внешний запрос — `GET /repos/24DSO-lab/kubron/releases/latest` к GitHub API без токена. Адрес зашит в код и не
  принимает пользовательских значений, поэтому защита от SSRF (ADR-0015) не требуется. Черновики, предрелизы и теги не в формате
  SemVer игнорируются.
- Условные запросы (`ETag`) не расходуют лимит API (60 запросов в час на адрес). Фоновая проверка идёт раз в сутки с разбросом
  ±10 %, после неудачи — раз в час; ручная проверка не чаще раза в минуту (иначе отдаётся кэш).
- Версии сравниваются строго по SemVer 2.0; предрелиз младше релиза. Любая версия, которая не разбирается, считается «не новее».

### 3. Определение способа установки

Явное указание надёжнее эвристик, поэтому чарт и образ сообщают способ сами; эвристики — запасной путь.

Веб-сервер (`KUBRON_INSTALL_METHOD` → иначе по окружению):

| Способ | Признак | Что показываем |
| --- | --- | --- |
| `helm` | `KUBRON_INSTALL_METHOD=helm`; чарт также задаёт `KUBRON_HELM_RELEASE` и `KUBRON_HELM_NAMESPACE` | `helm upgrade <релиз> oci://ghcr.io/<владелец>/charts/kubron --version <версия> --namespace <ns> --reset-then-reuse-values` |
| `kubernetes` | задана `KUBERNETES_SERVICE_HOST`, но не Helm | тег нового образа `ghcr.io/<владелец>/kubron:<версия>` |
| `docker` | файл `/.dockerenv`, `/run/.containerenv` или маркеры в `/proc/1/cgroup` | `docker pull …` и `docker compose pull && docker compose up -d` |
| `binary` | ничего из перечисленного | ссылка на релиз |

Десктоп (по пути исполняемого файла):

| Способ | Признак | Что показываем |
| --- | --- | --- |
| `deb` | Linux, файл `/usr/bin/kubron` и запись dpkg `/var/lib/dpkg/info/kubron.list` | ссылка на `.deb` и `sudo apt install ./<файл>` |
| `macos-app` | путь содержит `.app/Contents/MacOS/` | ссылка на `Kubron_<тег>_macos-universal.zip` |
| `archive` | остальные Linux и Windows | ссылка на архив своей ОС и архитектуры |

Если определить не удалось (`unknown`) или для архитектуры нет файла, остаётся только ссылка на релиз. Имя релиза Helm и
пространство имён проходят по белому списку символов (DNS-1123), версия — через разбор SemVer: в готовую команду не попадает
непроверенный текст.

### 4. Политика и права

- `KUBRON_UPDATE_CHECK=off` (в чарте `kubron.updateCheck: false`) запрещает любые запросы: сервер не обращается к сети, ручная
  проверка и переключатель в интерфейсе недоступны. Неверное значение на сервере — ошибка запуска; на десктопе — проверка
  выключена (при сомнении запросов нет).
- Десктоп: пользователь включает и выключает фоновую проверку; настройка хранится в каталоге Kubron. На сервере этот метод
  закрыт (`deniedMethods`): политику задаёт администратор развёртывания, а не пользователи страницы.
- `GetVersionInfo` доступен любому вошедшему пользователю (версию называют в обращениях в поддержку) и не ходит в сеть.
  `GetUpdateStatus` и `CheckForUpdates` требуют права `users.manage`: способ установки и имя релиза Helm — сведения о
  развёртывании. Эти методы — функции `App`, но `SetUpdates` и `StartUpdateChecks` — функции пакета, чтобы не попасть в привязки
  Wails и RPC.

### 5. Интерфейс

- Бейдж версии в шапке виден всем; у администратора рядом точка, если вышла новая версия.
- Администратору показывается баннер; скрытие запоминается для конкретной версии, на следующую он появится снова.
- Окно «Версия и обновления»: установленная и последняя версии, способ установки, команды с кнопкой «Копировать», ссылка на файл и
  контрольные суммы (`SHA256SUMS.txt`), ссылка на описание релиза, кнопка «Проверить» и (на десктопе) переключатель фоновой
  проверки. Тексты ошибок переводятся по коду (`update.error.<код>`); текст сетевых ошибок наружу не уходит.

## Последствия

- Закрытые сети: нужно выставить `kubron.updateCheck: false`. При включённой NetworkPolicy правило API-серверов по умолчанию
  пропускает порт 443 на любые адреса, поэтому GitHub доступен; при сужении `clusterApi.cidrs` доступ к `api.github.com` закрывается и
  проверка будет показывать ошибку сети (отключите её или добавьте правило в `networkPolicy.egress.extra`).
- Репозиторий релизов зашит в код: форк, публикующий свои релизы, должен изменить `update.DefaultRepo`.
- Автоматического обновления нет. Если оно понадобится для десктопа, оно потребует проверки подписи артефактов и отдельного ADR.
