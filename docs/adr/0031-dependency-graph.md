# ADR-0031: Граф зависимостей и цепочечная диагностика Kubron Intelligence

- Статус: предложено
- Дата: 2026-11-14
- Связано: ADR-0005, 0006, 0007, 0009, 0012, 0014, 0016, 0022, 0024, 0026; дополняет ADR-0024 (§2 «Сбор данных», §4 «Детерминированная диагностика», «Не входит: полный граф зависимостей»)

## Контекст

ADR-0024 реализован: `internal/diagnose` строит отчёт по Pod, Deployment и ReplicaSet, `internal/incident` хранит расследования. Диагностика целеориентирована и плоская:

- `diagnose.Collect` принимает только три вида цели (`Pod`, `Deployment`, `ReplicaSet`), остальное — `ErrUnsupportedTarget`;
- `diagnose.Context` — структура с типизированными полями (`Pods`, `Deployment`, `ReplicaSets`, `Namespace`, `Nodes`, `Events`). Каждый новый вид ресурса означал бы новое поле и новый ветвящийся сбор;
- причина «выше или ниже» цели распознаётся по тексту сообщения. Например, `pending.unbound_pvc` срабатывает на слово `persistentvolumeclaim` в сообщении планировщика, а затем отчёт предлагает человеку `step.check_pvc`. PVC, StorageClass и provisioner Kubron не читает;
- ряд шагов отчёта (`step.check_pvc`, `step.check_node_taints`, `step.check_node_capacity`) — это проверки, которые Kubron мог бы выполнить сам, но не выполняет.

На практике инженер ищет не причину в Pod, а причину неработающего приложения: Ingress, Service без endpoints, Deployment, не получивший ресурсы, Pod, ждущий PVC, PVC без provisioner, Node под давлением. Симптом и причина лежат в разных объектах (ADR-0024, Контекст).

Существующий `internal/k8s/graphbuild.go` строит граф для Argo CD и Flux. Для Intelligence он не подходит как код: работает через `kubernetes.Interface` напрямую, в обход `opsplatform.Reader`, allowlist и лимитера (ADR-0026 §1–2), и читает все Pod'ы namespace. Подходит как образец модели: идентификатор вершины `group/kind/namespace/name`, типизированные рёбра, `Warnings`, `Truncated`, предел размера.

Платформенный allowlist (`opsplatform/allowlist.go`) уже разрешает чтение Service, Endpoints, EndpointSlice, PVC, PV, StorageClass, Ingress, IngressClass, HPA, StatefulSet, DaemonSet, Job, CronJob, ConfigMap, Node. Собственный список диагностики (`diagnose.AllowedKinds`) уже: Pod, Namespace, Node, Event, ReplicaSet, Deployment.

## Решение

Настоящее решение вводит граф зависимостей как единую модель связей между ресурсами и переводит диагностику с «правила смотрят на набор объектов цели» на «правила обходят граф». Оно ограничено моделью, сбором и контрактом отчёта. Метрики (ADR-0032), группировка расследований (ADR-0033) и обратная связь (ADR-0034) — отдельные решения; настоящий ADR оставляет для них места в контракте (раздел 7).

Общие платформенные правила ADR-0026 (доступ только через `Reader`, права, аудит, deadline, лимитер, tenant scope) не повторяются и не меняются.

### 1. Отдельный пакет `internal/depgraph`

Модель и построитель графа живут в отдельном пакете `internal/depgraph`, а не внутри `diagnose`: граф нужен и диагностике, и карте зависимостей в интерфейсе, и потенциально `readiness` и `drift`.

- Пакет не знает про платформу (`opsplatform`), `Store`, `incident` и приложение. Чтение кластера — через узкий интерфейс `Reader` (`Get`, `List`), объявленный в самом пакете, по образцу `diagnose.Reader` (подмножество `opsplatform.Reader`, адаптер живёт в слое связки).
- В слое связки остаётся один адаптер платформенного `Reader`. Диагностика и граф используют один набор потребительских типов чтения и ошибок (`ListOptions`, `ListResult`, `ErrNotFound`, `ErrForbidden`, `ErrUnavailable`, `ErrTooLarge`); способ (псевдонимы типов или общий подпакет) выбирается при реализации при условии одного адаптера.
- `diagnose` импортирует `depgraph`. Обратной зависимости нет.
- `internal/k8s/graphbuild.go` остаётся как есть: он обслуживает GitOps-графы и не переписывается. Его модель и именование вершин — образец, код не переиспользуется.

### 2. Модель графа

**Вершина** — ресурс кластера: группа, вид, namespace, имя, UID, состояние.

- Для идентификации ресурсов вводится поле `Group` в `diagnose.ResourceRef` (`json:"group,omitempty"`). Без группы вид неоднозначен (core `Event` и `events.k8s.io/Event`, `extensions/Deployment` и `apps/Deployment`). Поле необязательное: сохранённые инциденты без него остаются валидными.
- Состояние вершины использует существующий словарь здоровья графа: `Healthy`, `Degraded`, `Progressing`, `Suspended`, `Missing`, плюс `Unknown` — ресурс не удалось прочитать.

**Различие «нет» и «не знаем»** — ключевое правило модели. Состояние `Missing` ставится только когда кластер ответил `NotFound`. Отказ RBAC, недоступность источника, лимит размера, достижение предела графа и вид, запрещённый политикой (Secret), дают `Unknown` с кодом причины (`forbidden`, `unavailable`, `too_large`, `limit`, `policy`). Это продолжение принципа `MissingContext` из ADR-0024 §4: отсутствие данных не должно выглядеть как отсутствие проблемы.

**Ребро** — типизированная связь `From → To` с состоянием. Типы рёбер:

| Тип | Направление | Источник связи |
|---|---|---|
| `owns` | владелец → дочерний | ownerReferences (Deployment → ReplicaSet → Pod, StatefulSet → Pod, CronJob → Job → Pod) |
| `selects` | Service → Pod | `spec.selector` |
| `backed_by` | Service → EndpointSlice | метка `kubernetes.io/service-name` |
| `routes` | Ingress → Service | backend правил и `defaultBackend` |
| `mounts` | Pod → PVC, ConfigMap, Secret | `spec.volumes`, `envFrom`, `env.valueFrom` |
| `binds` | PVC → PV, PVC → StorageClass | `spec.volumeName`, `spec.storageClassName` |
| `runs_on` | Pod → Node | `spec.nodeName` |
| `scales` | HPA → workload | `spec.scaleTargetRef` |

Состояние ребра: `ok`, `broken` (обе стороны есть, но связь не работает: селектор не совпал, PVC не привязан), `missing` (цель ссылки не найдена, `NotFound`), `unknown` (прочитать не удалось).

**Отсутствующая связь — часть графа, а не отсутствие ребра.** Это решение нужно для подсветки проблем:

- ссылка по имени на несуществующий объект (PVC, ConfigMap, backend Ingress) представляется вершиной-заглушкой в состоянии `Missing` и ребром `missing`;
- селектор, не нашедший целей (Service без Pod), представляется состоянием `Degraded` вершины-источника с фактом отчёта; пустое множество не рисуется как «нет рёбер».

**Secret.** Kubron не читает Secret (ADR-0024 §2). Ссылка на Secret попадает в граф вершиной в состоянии `Unknown` с причиной `policy`; проверка существования остаётся шагом для человека (как сейчас `step.check_referenced_object`).

**ConfigMap.** Для проверки ссылок читается только факт существования. Поля `data` и `binaryData` отбрасываются в `depgraph` сразу после чтения, до передачи вызывающему коду: они не попадают ни в `Context`, ни в отчёт, ни в хранилище, ни в журнал. Это закрепляется отдельным тестом. Если платформенный `Reader` получит режим чтения только метаданных, `depgraph` переходит на него без изменения контракта.

### 3. Построение графа: от цели, ограниченно

Граф строится **от цели расследования**, а не по всему кластеру, в двух направлениях: вверх по владельцам и потребителям (Pod → ReplicaSet → Deployment; Pod ← Service ← Ingress; HPA → цель) и вниз/вбок по зависимостям (Pod → PVC → PV/StorageClass, Pod → Node, Deployment → Pod).

- **Чтение точечное:** по имени из ссылки (`Get`), по селектору (`List` с `LabelSelector`), по полю (`List` с `FieldSelector`, например Pod'ы Node по `spec.nodeName`). Список всех объектов вида в namespace допустим только там, где иначе связь не найти (Service → Pod: список Service namespace и локальное сопоставление селекторов; PVC StatefulSet: один `List` PVC namespace вместо `Get` на каждый), и всегда с `Limit`.
- **Пределы** (в коде как верхняя граница, не настраиваются, меняются только новым ADR): 200 вершин, 600 рёбер, глубина 4 шага от цели, не более 40 запросов чтения на построение графа сверх уже выполняемых диагностикой. Превышение — `Truncated` в графе и запись в `Partial` отчёта; результат остаётся частичным графом, а не ошибкой.
- **Нагрузка на кластер** укладывается в лимитер ADR-0026 (стартовое значение 4 одновременных чтения на кластер) и общий deadline операции. Постоянные informers и кэш графа не вводятся (ADR-0026 §2: informers только при обоснованной потребности); операция остаётся короткой и синхронной (ADR-0026 §8).
- **Ошибки чтения** одной связи не роняют сбор: они становятся состоянием `Unknown` и `MissingContext` по правилам, уже действующим в `diagnose.Collect`.
- Граф — **снимок на момент расследования**, а не живая модель. Обновление — повторным открытием или обновлением расследования, как для Events.

### 4. Контекст диагностики

`diagnose.Context` получает поле `Graph` и помощники обхода (`Owners(node)`, `Dependents(node)`, `Edges(node, type)`, `PathTo(kind)`). Типизированные поля `Pods`, `Deployment`, `ReplicaSets`, `Nodes` сохраняются как есть: существующие правила не переписываются целиком. Новые правила читают объекты через граф. Значения из объектов (conditions, spec) хранятся в `Context` в типизированном виде; в отчёт и хранилище попадают только коды, параметры и отредактированные сообщения (ADR-0022, ADR-0024 §5).

`diagnose.Collect` перестаёт быть привязан к фиксированному `switch` по видам цели: для каждого поддерживаемого вида цели регистрируется стартовая точка построения графа (раздел 6).

### 5. Цепочечные находки: кандидат первопричины, а не первопричина

Типы записей отчёта сохраняются из ADR-0024 §3 (факт, гипотеза, рекомендация, шаг). Вводится связь между гипотезами:

- `Hypothesis.Explains []string` — идентификаторы гипотез отчёта, которые эта гипотеза объясняет. Пример: гипотеза «PVC не привязан: StorageClass не найден» на PVC объясняет гипотезу «Pod не запланирован: PVC не привязан» на Pod.
- Гипотеза, которая объясняет другие и сама не объясняется ни одной, помечается интерфейсом как **кандидат первопричины**. Значения «первопричина установлена» и поля роли `root_cause` в контракте нет: подтвердить причину может только человек (`incident.Outcome`, ADR-0024 §3). Уверенность по-прежнему `low`, `medium` или `high`.
- Путь по графу от затронутого ресурса до кандидата — подтверждающие факты: каждое звено цепочки — факт с источником, полем и временем наблюдения (`Fact.Source`, `Fact.ObservedAt`).
- Рекомендации и шаги привязываются к гипотезам, как сейчас.

`Hypothesis` и `Recommendation` получают поле `RuleID` — идентификатор правила, которое их выдало (значения уже есть в таблице правил движка: `pod.pending`, `pod.crash_loop` и т. д.). Сегодня у записи есть `Code`, но нет правила-источника, а версия одна на весь набор. `RuleID` нужен для сопоставления с исходами расследований (ADR-0034) и для проверяемости изменений диагностики.

`RuleSetVersion` поднимается до 2: изменился контракт отчёта и состав правил. Сохранённые инциденты версии 1 читаются без изменений (новые поля необязательны), интерфейс корректно показывает отчёт без графа.

### 6. Цели диагностики и порядок внедрения

Новые виды цели и правила добавляются этапами по практической ценности; этап завершён, когда у него есть правила, фикстуры и локализованные коды.

**Этап 1: цепочка Pod и хранилище, Service, Node**

| Цель / цепочка | Что читается | Что диагностируется |
|---|---|---|
| Pod → PVC → PV / StorageClass | PVC, PV, StorageClass, Events PVC | `Pending` из-за PVC находится по графу, а не по тексту: класс не найден, нет класса по умолчанию, `WaitForFirstConsumer` без потребителя, ошибки provisioner по Events (`ProvisioningFailed`), PVC в `Lost`. Текстовое правило `pending.unbound_pvc` остаётся запасным с пониженной уверенностью |
| Service | EndpointSlice, Pod по селектору, Ingress → Service | селектор не совпал ни с одним Pod; Pod не `Ready` (endpoints пусты); порт и `targetPort` не совпали с портами контейнера |
| PVC (как цель) | StorageClass, PV, Pod'ы-потребители, Events | Pending и Lost, ошибки attach и mount по Events потребителя |
| Node (как цель и звено цепочки) | conditions, taints, allocatable, Pod'ы Node по `spec.nodeName`, Events Node | `NotReady`, давление на память, диск и PID, `Unschedulable`, затронутые Pod'ы; существующая гипотеза `oom.node_memory_pressure` использует это звено |

**Цели уровня кластера.** Node является целью расследования с этапа 1: namespace у цели допускается пустым только для Node. Список Pod'ов Node читается `List` по `spec.nodeName` без namespace; при ограниченном RBAC (namespace scoping) это `Unknown` с причиной `forbidden`, а список затронутых Pod'ов помечается неполным в `Partial`. PV целью не является: PV диагностируется как звено цепочки PVC (цель — PVC).

**Этап 2: вход и масштабирование**

| Цель / цепочка | Что читается | Что диагностируется |
|---|---|---|
| Ingress | Service-backend, EndpointSlice, IngressClass | backend Service отсутствует или без endpoints; IngressClass не найден; TLS Secret не читается: остаётся шагом для человека |
| HPA | `scaleTargetRef`, conditions (`AbleToScale`, `ScalingActive`, `ScalingLimited`) | цель отсутствует; метрики недоступны (по сообщению условия); достигнут `maxReplicas` |
| ConfigMap-ссылки Pod | существование ConfigMap | `config.missing_reference` подтверждается графом, а не только сообщением kubelet |

**Этап 3: контроллеры с состоянием и задания**

| Цель / цепочка | Что читается | Что диагностируется |
|---|---|---|
| StatefulSet | Pod'ы, PVC по `volumeClaimTemplates`, ревизии | застревание на Pod N при упорядоченном запуске; PVC Pending; `partition` в стратегии обновления |
| Job | Pod'ы Job, conditions | `BackoffLimitExceeded`, `DeadlineExceeded`; причина падения Pod'а разбирается существующими правилами Pod |
| CronJob | Job'ы, `suspend`, `lastScheduleTime` | расписание приостановлено, пропущенные запуски (`startingDeadlineSeconds`), блокировка по `concurrencyPolicy` |

Все виды чтения входят в платформенный allowlist ADR-0026. Собственный список `diagnose.AllowedKinds` расширяется по этапам; существующий страж («виды диагностики ⊆ allowlist платформы») распространяется на новые виды. Новые права Kubernetes RBAC для технической учётной записи — только `get` и `list` перечисленных видов; запись и чтение Secret не вводятся. Если права на вид нет, это `Unknown` с причиной `forbidden` и `MissingContext` в отчёте, а не ошибка расследования.

### 7. Контракт отчёта и места для следующих решений

К `diagnose.Report` добавляется необязательное поле `Graph`: снимок графа (вершины с состоянием и причиной, рёбра с типом и состоянием, признак `Truncated`, предупреждения). Поле хранится в инциденте вместе с отчётом (ADR-0024 §5): без снимка история теряет контекст, как и без снимка Events. В снимок попадают только идентификаторы ресурсов, коды состояний и причин; значения полей объектов, хосты и пути Ingress, данные ConfigMap, аннотации и метки не сохраняются.

Для последующих решений контракт оставляет:

- ADR-0032 (метрики): шаги вида `step.check_memory_metrics` — места, где метрики станут автоматическим доказательством; граф даёт адресацию (Pod, Node, PVC) для запросов;
- ADR-0033 (корреляция): общие вершины графа (Node, PVC, StorageClass, ConfigMap) — основание для группировки расследований в момент открытия по живым данным;
- ADR-0034 (обратная связь): `RuleID` и `Explains` — ключи для статистики правил и цепочек.

### 8. Интерфейс

Настоящий ADR фиксирует данные, нужные интерфейсу: вершины, рёбра, состояния, отсутствующие связи, кандидаты первопричины и затронутые ресурсы (`Report.Resources`). Поставка интерфейса разбита на два шага:

- **Этап 1:** компактное представление цепочки в отчёте: путь по графу от затронутого ресурса до кандидата первопричины, вершины с состоянием, `Missing` и `Unknown` помечены явно. Это закрывает задачу «почему не работает приложение» без интерактивной карты.
- **После этапа 2:** интерактивная карта зависимостей. Она нужна после появления рёбер Ingress → Service и HPA → цель, иначе карта неполна относительно задачи; к этому моменту контракт графа стабилизируется на практике.

Выбор библиотеки визуализации и экранов фиксируется при реализации и не требует отдельного ADR. Адресные события и RPC — по ADR-0009 и ADR-0026 §7: событие несёт только идентификатор, подробности клиент загружает RPC с повторной проверкой прав.

## Рассмотренные альтернативы

- **Расширить `k8s/graphbuild.go`.** Отклонено: работает через `kubernetes.Interface` в обход `Reader`, allowlist и лимитера (ADR-0026 §1–2), читает все Pod'ы namespace, привязан к GitOps-DTO.
- **Граф внутри пакета `diagnose`.** Отклонено: граф нужен интерфейсу и другим доменам, а `diagnose` не должен владеть общей моделью связей.
- **Граф всего кластера или namespace.** Отклонено: стоимость на больших кластерах, превышение лимитера, нечитаемость; расследование начинается с цели.
- **Постоянный informer-кэш графа.** Не выбрано: ADR-0026 §2 допускает informers только при обоснованной потребности; текущая потребность закрывается коротким построением от цели. Возвращаемся к вопросу, если построение окажется слишком дорогим на практике.
- **Живое обновление графа в интерфейсе.** Отклонено на этом этапе: значительно дороже снимка, ценность для расследования та же.
- **Поле роли `root_cause` у гипотезы.** Отклонено: противоречит ADR-0024 §3; гипотеза не становится установленной причиной без решения человека. Вместо роли — связь `Explains` и вычисляемый признак «кандидат».
- **Правила по тексту сообщений вместо графа.** Остаётся запасным путём (этап 1), но не основой: текст зависит от версии Kubernetes и компонентов.
- **Хранить в инциденте граф со значениями полей.** Отклонено: расширяет поверхность утечки данных (ADR-0022); достаточно идентификаторов и кодов состояний.
- **Читать ConfigMap целиком и не отбрасывать данные.** Отклонено: данные ConfigMap могут содержать чувствительные значения; нужен только факт существования.

## Последствия

- Появляется общая модель связей ресурсов; диагностика перестаёт зависеть от фиксированного набора полей контекста.
- Правила, которые сегодня заканчиваются «шагом для человека», становятся автоматическими проверками с фактами; шаги остаются только для того, что Kubron сделать не может (Secret, образ в registry, сеть вне кластера).
- Каждый этап расширяет объём чтения кластера: растёт число запросов на расследование (ограничено разделом 3), меняются `diagnose.AllowedKinds` и требования к RBAC технической учётной записи. Это отражается в документации по развёртыванию и в CHANGELOG.
- Контракт отчёта меняется аддитивно: `Group` в `ResourceRef`, `Graph` в `Report`, `RuleID` и `Explains` в записях; `RuleSetVersion = 2`. Сохранённые инциденты версии 1 остаются читаемыми. Если `pgstore` хранит отчёт как документ, миграция схемы не нужна; это проверяется при реализации контрактными тестами `incident/incidenttest`.
- Новые коды фактов, гипотез, рекомендаций и шагов локализуются по ADR-0014. Новые правила тестируются на фикстурах объектов Kubernetes и Events (ADR-0024 §4); для каждой цепочки нужны фикстуры с отсутствующими, запрещёнными и усечёнными данными.
- Снимок графа увеличивает размер записи инцидента (верхняя граница задана разделом 3) и подпадает под retention инцидента (ADR-0024 §5, п. 7).
- Чтение ConfigMap ради проверки существования требует гарантии, что содержимое не сохраняется: обязательный тест (содержимое ConfigMap не попадает в `Context`, отчёт, хранилище и журнал).
- Главный риск — ложные выводы по цепочке. Каждая гипотеза обязана показывать путь по графу и недостающие данные; различие `Missing` и `Unknown` обязательно для интерфейса.

## Согласовано при обсуждении (2026-11-14)

- Это решение оформляется новым ADR, а не правкой ADR-0024 (принятые ADR не переписываются).
- Граф — отдельный пакет, а не часть `diagnose`.
- Корреляция расследований (ADR-0033) будет строиться в момент открытия расследования по живым данным кластера, а не по постоянному индексу.
- Метрики (ADR-0032) начинаются со встроенного стека мониторинга Kubron; подключение внешнего Prometheus-совместимого источника и связанная защита от SSRF откладываются.
- ADR записываются прямо в ветку `refactor`.

## Решения по ранее открытым пунктам (2026-11-14)

Приняты исходя из того, что лучше для продукта, при условии подтверждения тимлидом.

1. **Пределы графа: 200 вершин, 600 рёбер, глубина 4, 40 запросов.** Принято как стартовые значения, закреплённые в коде. Глубина 4 покрывает самые длинные нужные цепочки (Ingress → Service → Pod → PVC → PV; Pod → ReplicaSet → Deployment плюс Pod → Node); 40 запросов хватает при условии, что связи с неизвестным числом объектов (PVC StatefulSet, Service namespace) читаются одним `List`, а не `Get` на каждый. Значения пересматриваются новым ADR по результатам измерений на реальных кластерах, а не настройкой.
2. **Имена полей: `Explains`, `RuleID`, `Group`.** Принято. `Explains` описывает связь, а не оценку, и не подразумевает установленной причины; `RuleID` совпадает с идентификаторами правил движка; `Group` — стандартный термин Kubernetes API.
3. **Чтение существования ConfigMap: да, на этапе 2, с отбрасыванием `data` и `binaryData`.** Принято. Полагаться только на сообщение kubelet хуже: оно зависит от версии и локали компонентов и не показывает цепочку. Риск утечки закрыт отбрасыванием данных на границе `depgraph`, обязательным тестом и возможностью перейти на чтение метаданных, когда платформа его поддержит.
4. **Цели уровня кластера: Node — цель с этапа 1; PV — только звено цепочки.** Принято. Node нужен как самостоятельная цель (давление, taints, затронутые Pod'ы) и уже читается диагностикой. PV не нужен как цель: диагностика хранилища начинается с PVC, а отдельная цель PV добавляла бы вид без пользовательского сценария.
5. **Карта зависимостей в интерфейсе: после этапа 2; на этапе 1 — компактное представление цепочки в отчёте.** Принято. Карта без рёбер Ingress → Service и HPA → цель неполна; контракт графа стабилизируется на этапе 1; компактная цепочка уже даёт пользователю ответ «почему не работает приложение».

Открытых вопросов нет. Статус остаётся «предложено» до принятия решения тимлидом.
