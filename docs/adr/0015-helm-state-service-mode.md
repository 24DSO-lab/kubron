# ADR-0015: Состояние Helm в сервисном режиме и защита от SSRF

- Статус: принято
- Дата: 2026-10-30
- Связано: ADR-0006, 0007, 0008, 0012; `docs/tickets/stage-3.md` (3.1c, 3.2, 3.7)

## Контекст

Helm в Kubron хранит состояние файлами в `GetKubronDir()/helm` (`helmHomeDir()`): `repositories.yaml`
(в нём пароли репозиториев открытым текстом), `oci.yaml` и `registry-config.json` (OCI-реестры и их
учётные данные), `operations.json` (журнал операций, 200 записей), `cache/` (индексы и списки тегов).
Для сервиса (кластеры в PostgreSQL) это не подходит:

1. Файлы общие для всех пользователей: команды видят репозитории и журнал друг друга (ADR-0012).
2. В Helm-чарте Kubron каталоги лежат на `emptyDir` и пропадают при перезапуске пода; с несколькими
   репликами у каждой были бы свои файлы.
3. Пароли репозиториев лежат открытым текстом, что противоречит ADR-0008.
4. URL репозиториев и реестров ничем не ограничены: сервер выполняет запрос на адрес, который прислал
   пользователь (metadata-сервис облака, внутренние службы) — SSRF.
5. Helm читает kubeconfig файлом, а для кластеров из БД файла нет (ограничение, записанное в 3.0 и 3.7).

## Решение

### 1. Где хранится состояние

Список репозиториев, OCI-реестры с учётными данными и журнал операций — в **PostgreSQL, область — команда**
(`team_id`). Интерфейс `k8s.HelmStateStore` с двумя реализациями по образцу `internal/store`:

- файловая — прежнее поведение, без изменений (десктоп и режим одного пользователя);
- PostgreSQL — в `pgstore`, подключается в `store.FromPostgres` как `Store.HelmState()`.

Кэш индексов и списков тегов остаётся на диске (`emptyDir`): это воспроизводимые данные. Ключ кэша —
`<team_id>/<имя>`, чтобы одноимённые репозитории разных команд не пересекались. Потеря кэша стоит одной
повторной загрузки индекса.

### 2. Схема (миграция `0005`, с `down`)

Одна таблица на репозитории обоих видов (имя уникально в команде независимо от вида, как сейчас делает
`nameTaken`), одна на журнал:

```
helm_repositories
  id            uuid PK
  team_id       → teams(id) ON DELETE CASCADE
  name          text        UNIQUE (team_id, name)
  kind          text        CHECK in ('http', 'oci')
  url           text        без учётных данных в самом URL
  username      text
  options       jsonb       insecureTLS, plainHTTP, charts (список чартов OCI)
  secret_enc    bytea NULL  пароль/токен, secretbox
  secret_key_id text        CHECK (secret_enc IS NULL OR secret_key_id <> '')  — как в 0003
  created_by    → users(id) ON DELETE SET NULL
  created_at, updated_at

helm_operations
  PK (team_id, id), team_id → teams(id) ON DELETE CASCADE
  cluster_id → clusters(id) ON DELETE SET NULL        (журнал переживает кластер; имя кластера лежит в записи)
  finished_at timestamptz, record jsonb                (запись операции целиком; в колонки вынесено то, по чему выбирают)
  индекс (team_id, finished_at DESC)
```

Пароль HTTP-репозитория тоже шифруется (в задании названы только OCI, но в `repositories.yaml` пароль
лежит открытым текстом — переносить его в БД в таком виде нельзя).

Журнал по-прежнему хранит последние 200 операций, теперь — на команду; `ClearHelmOperations` очищает
журнал только своей команды. Это операционный журнал, а не аудит: кто и что сделал, фиксирует аудит
(действия пишутся в `audit.actions.*` с `teamId` и `clusterId`).

### 3. Шифрование

`secretbox`, AAD вида `helm/<team_id>/<name>`, идентификатор ключа в `secret_key_id` — как `0003`.
Привязка к команде и имени не даёт скопировать шифротекст в другую строку. Следствие: **репозиторий
нельзя переименовать на месте** (имя входит в AAD) — переименование = удалить и добавить заново; в UI
такой операции и сейчас нет. `kubron-server rekey` перешифровывает и эти секреты, вывод получает строку
«helm secrets».

OCI: файл `registry-config.json` в сервисном режиме не используется и не создаётся. Учётные данные реестра
передаются клиенту реестра Helm из памяти (`ClientOptAuthorizer` с `auth.StaticCredential`) и отдаются только
хосту этого реестра; Docker-конфигурация сервера не читается. Вход в реестр (`Login`) при добавлении заменён
проверочным запросом тегов. Файловый режим по-прежнему использует `registry-config.json`.

### 4. Изоляция

Каждый метод хранилища принимает `team_id` (команда активного кластера или явный `authzCluster`);
чужое имя и чужой идентификатор операции → «не найдено» (как 3.2). Секреты не возвращаются через API
(`HelmRepoInfo` несёт только `username` и признак «пароль задан») и не пишутся в логи.

### 5. Доступ к кластеру из БД

`RESTClientGetter` поверх `*rest.Config` менеджера подключений (PR 2): копия самого конфига, без
записи токенов и паролей в kubeconfig или временные файлы, потому что токен `oidc-password` обновляется
через `WrapTransport`.

### 6. Защита от SSRF: пакет `internal/netpolicy`

Проверка выполняется **на каждом соединении** (`net.Dialer.Control` получает уже разрешённый числовой
адрес), а не разбором URL заранее: это закрывает подмену DNS между проверкой и соединением. Редиректы
проверяются заново (`CheckRedirect`); у `http.Transport` отключается прокси из окружения (иначе запрос
к внутреннему адресу ушёл бы на прокси, а проверялся бы адрес прокси).

Всегда запрещено: loopback, link-local (`169.254/16`, `fe80::/10`), unspecified (`0.0.0.0/8`, `::`),
multicast, широковещательный `255.255.255.255` и известные адреса служб метаданных
(`169.254.169.254`, `fd00:ec2::254`, `168.63.129.16`, `100.100.100.200`). Адрес сначала нормализуется:
IPv4-mapped `::ffff:a.b.c.d`, NAT64 `64:ff9b::/96`, 6to4 `2002::/16`, IPv4-translated и устаревший
IPv4-compatible IPv6 проверяются по вложенному IPv4; хосты в записи `2130706433`, `0177.0.0.1`, `0x7f.1`,
`127.1` приводятся к обычному виду до любой проверки и до обращения к резолверу.

Профили:

| Класс соединений | Профиль | Запрещено дополнительно |
|---|---|---|
| Helm-репозитории, индексы и чарты, OCI | `strict` | `10/8`, `172.16/12`, `192.168/16`, `fc00::/7`, `100.64/10` |
| Адрес API-сервера кластера | `permissive` | — |

Предложение по умолчанию подтверждается: API-серверы кластеров обычно в частных сетях, а репозиторий
чартов на внутреннем адресе — осознанное исключение оператора, а не норма.

**Исключения.** Список CIDR в переменной окружения оператора. Они снимают запрет с loopback, link-local и
(в `strict`) частных диапазонов, но **никогда** — с unspecified, multicast и адресов метаданных:
ошибочная настройка не должна открывать metadata-сервис. Переменные:
`KUBRON_HELM_ADDR_POLICY` (`strict` по умолчанию на сервере, `off` — выключить),
`KUBRON_HELM_ALLOW_CIDRS` (реализованы в PR 3), `KUBRON_CLUSTER_ADDR_POLICY` (по умолчанию `off`, затем
`permissive`/`strict`) и `KUBRON_CLUSTER_ADDR_ALLOW_CIDRS` (PR 4).

**Включение** по образцу `k8s.SetConnectionPolicy`: `cmd/kubron-server` вызывает `netpolicy.Set(scope, p)`
при старте; десктоп и режим одного пользователя не вызывают, `netpolicy.For` возвращает `nil`, и все
методы `nil`-политики ничего не ограничивают.

**Ответ на блокировку** неотличим от отказа в соединении (`dial tcp …: connection refused`), чтобы сервер
нельзя было использовать как сканер внутренней сети. Причина (адрес, класс, политика) пишется только в
серверный лог — без URL, учётных данных и параметров запроса.

Реализация для API-сервера (PR 4): проверка адреса в `CheckKubeconfigPolicy` (при добавлении и при каждом подключении),
`rest.Config.Dial` для REST, discovery, informers и Helm, а терминал и port-forward открывают соединение через
`UpgradeTransport` SPDY (стандартный дайлер `rest.Config.Dial` не использует); `proxy-url` отклоняется, прокси из
окружения отключается; `in-cluster` не проверяется. Адрес IdP для `oidc-password` входит в ту же политику (журнал решений, D-06).

Для API-сервера кластера политика изначально была выключена, потому что e2e в CI использует kind с
API-сервером на `127.0.0.1`. Это изменено, см. «Дополнение: политика по умолчанию и IdP» ниже.

## Рассмотренные альтернативы

- **PVC под `helm/`.** Не решает изоляцию команд и пароли открытым текстом, а `ReadWriteOnce` ограничивает
  число реплик одним подом. Отклонено.
- **Хранить состояние в Secret/ConfigMap Kubernetes.** Смешивает данные приложения с рабочим кластером и
  требует прав на запись в нём. Отклонено.
- **Область — пользователь.** Команда делится репозиториями (так работает и доступ к кластерам, ADR-0012);
  личные репозитории не требуются. Отклонено.
- **Проверка только URL и результата резолвинга перед запросом.** Не защищает от DNS rebinding и редиректов.
  Отклонено в пользу проверки на соединении.
- **Список запретов вместо профилей.** Сложнее объяснить и проверить; два профиля покрывают оба случая.

## Последствия

- Репозитории, учётные данные и журнал изолированы по командам, переживают перезапуск пода и работают на
  нескольких репликах; PVC под Helm не нужен, `emptyDir` остаётся только для кэша.
- Бэкап БД включает состояние Helm; потеря ключа шифрования = потеря паролей репозиториев (ADR-0008),
  ротация и `rekey` покрывают их.
- Откат `0004` удаляет репозитории и журнал Helm.
- Существующее файловое состояние в БД автоматически не переносится. Это можно добавить в
  `kubron-server import-files` отдельной задачей (см. «Вопросы»).
- Прокси из окружения для Helm-запросов не используется; если в организации выход наружу возможен только
  через прокси, нужен отдельный ADR (проверка целевого адреса на стороне прокси).
- `strict` по умолчанию сломает репозитории на внутренних адресах, пока оператор не добавит их в
  `KUBRON_HELM_ALLOW_CIDRS`; это нужно описать в `docs/deploy.md` (PR 3).
- Каждая блокировка — строка в логе; при сканировании это шум, ограничение частоты — вне этого ADR.

## Дополнение: политика по умолчанию и IdP

- **Политика адреса API-сервера включена по умолчанию в сервисном режиме** (`KUBRON_CLUSTER_ADDR_POLICY=permissive`;
  сервисный режим — БД или адрес не на loopback, `Config.ServiceMode`). Вне сервисного режима (один пользователь на
  loopback, десктоп) по умолчанию `off`. Явное `off` в сервисном режиме допустимо, но сервер пишет предупреждение:
  без политики пользователь направляет сервер на loopback, link-local и metadata-сервис облака.
- **Исключения действительно переопределяют запрет loopback**: `classify` помечает loopback и link-local как
  снимаемые списком `Allow`, а метаданные, unspecified и multicast — нет. Поэтому e2e на kind (API-сервер на
  `127.0.0.1`) работает с `KUBRON_CLUSTER_ADDR_ALLOW_CIDRS=127.0.0.0/8` (jobs `e2e-pg` и `e2e-ha` в `ci.yml`), а политика
  остаётся включённой и проверяется теми же e2e; отдельный `off` для CI не нужен. Файловые e2e работают вне
  сервисного режима и политики не имеют.
- **IdP для `oidc-password`** (discovery, `token_endpoint` из ответа IdP, обновление токена и повторный вход)
  использует тот же дайлер-уровневый guard (`idpHTTPClient`: `DialContext`, проверка редиректов, прокси из окружения
  отключён) и ту же политику `ScopeClusterAPI`; отдельной переменной нет. **Рекомендуемый профиль — `permissive`**:
  loopback, link-local и метаданные закрыты, внутренний IdP в частной сети работает без настройки. `strict` закрывает
  и частные сети, тогда адрес IdP нужно добавить в `KUBRON_CLUSTER_ADDR_ALLOW_CIDRS`. Запросы к IdP покрыты тестами:
  metadata, loopback, link-local, редирект на запрещённый адрес, `token_endpoint` на запрещённом адресе, подмена DNS на
  соединении и обновление токена после закрытия адреса.
- `proxy-url` в kubeconfig запрещён при любом включённом профиле (`ErrClusterProxyForbidden`).

## Вопросы владельцу

1. Подтвердить профили (Helm — `strict`, API-сервер — `permissive`) и то, что исключения не снимают запрет
   с метаданных, unspecified и multicast.
2. Переносить ли существующие `repositories.yaml`/`oci.yaml`/`operations.json` в БД через `import-files`.
3. Нужен ли выход через корпоративный прокси для Helm-запросов.
