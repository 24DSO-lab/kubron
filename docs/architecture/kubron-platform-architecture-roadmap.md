# Kubron A+B+C: целевая архитектура и roadmap

- Статус: **проектное предложение, не утверждённый ADR**
- Дата: 2026-11-26
- Базовая ветка: `refactor`
- Базовый commit: [`3fa8504b02c49070d0b2e57aa85953d2cecf36ee`](https://github.com/24DSO-lab/kubron/commit/3fa8504b02c49070d0b2e57aa85953d2cecf36ee)
- Область: Control Plane + Operations Platform + Intelligence Platform + Autonomy Level 3
- Ограничение этапа: архитектурное проектирование; production-код и runtime-поведение не меняются

## 1. Резюме

**Kubron должен развиваться как единая Kubernetes Operations & Intelligence Platform**, которая управляет несколькими кластерами, помогает выполнять ежедневные операции, понимает состояние инфраструктуры и постепенно получает возможность выполнять разрешённые действия автономно.

Целевая модель состоит из четырёх взаимосвязанных capabilities:

1. **Control Plane** — каталог кластеров и групп, идентичность, доступ, контекст и координация.
2. **Operations Platform** — Kubernetes, Helm, GitOps, диагностика эксплуатации, Lifecycle и выполнение изменений.
3. **Intelligence Platform** — доказательства, граф зависимостей, диагностика, корреляция, объяснения и рекомендации.
4. **Autonomy Layer** — политики, планы, approvals, исполнение, проверка результата и recovery.

Это **не четыре отдельных продукта и не четыре обязательных микросервиса**. Это логические слои одного продукта и одного согласованного архитектурного контура.

Целевая автономность — **уровень 3: Autonomous Operations**. Архитектуру следует проектировать с учётом этого уровня, но внедрять его поэтапно. Ближайшая работа — не автоматическое исправление кластеров, а проектирование общих контрактов, политик и жизненного цикла операции.

## 2. Исходная архитектурная база

Ветка `refactor` уже содержит значительную часть платформы:

| Область | Существующая основа |
|---|---|
| Управление кластерами | `internal/app`, cluster manager, `ForSession`, `ConfigFor`, credential providers |
| Организации и команды | `internal/tenant`, `internal/teams`, каталог кластеров |
| Авторизация | `internal/auth`, app-RBAC, пересечение с Kubernetes RBAC |
| Операции Kubernetes | `internal/k8s`, Helm, Argo CD, Flux |
| Безопасное чтение | `internal/opsplatform`, allowlist, limiter, partial results |
| Intelligence | `internal/diagnose`, `depgraph`, `signals`, `correlation`, `incident`, `feedback` |
| Lifecycle | `internal/readiness`, `baseline`, `drift` |
| Хранение | `internal/store`, `internal/pgstore`, файловая реализация |
| HA и доставка | `internal/jobs`, `replicaevents`, Event Hub, PostgreSQL advisory locks |
| Безопасность и аудит | `internal/audit`, `secretbox`, `secrets`, `logging`, `logredact` |

### 2.1. Архитектурные решения, которые сохраняем

- ADR-0005: общий пул подключений и сессионное представление кластеров.
- ADR-0006, 0012, 0018: текущая модель доступа, tenancy и получения credentials.
- ADR-0007, 0008, 0016: Store, шифрование и HA.
- ADR-0009, 0022: адресные события, аудит, журналирование и редакция чувствительных данных.
- ADR-0024…0027: Intelligence, Lifecycle, общая платформа и baseline/drift.
- ADR-0031…0034: Dependency Graph, metrics evidence, correlation/problems и feedback.

Эти решения не переписываются ради новой общей абстракции. Новые capabilities должны расширять существующие узкие контракты.

### 2.2. Ограничения, которые нельзя игнорировать

1. `internal/opsplatform` — безопасная платформа сбора данных, а не исполнитель произвольных изменений.
2. `internal/jobs` — механизм периодических служебных задач. Он не является очередью долговременных пользовательских операций с состояниями, отменой и восстановлением.
3. Активный кластер сессии удобен для интерактивного UI, но не может быть неявной целью автономной операции. Исполнение должно получать явный cluster/resource scope.
4. Event Hub и межрепличные события — транспорт уведомлений, а не источник истины о состоянии выполнения.
5. Нельзя полагаться на память одной реплики для состояния операции, approval или блокировки.
6. Нельзя объединять доменные данные Intelligence, Lifecycle и Operations в одну универсальную схему.
7. Нельзя расширять Kubernetes RBAC или app-RBAC автоматически только потому, что появился новый сценарий.

Схема показывает логические зависимости, а не сетевые границы. В обозримой перспективе предпочтительна **модульная монолитная архитектура**: единый Go application с явными границами пакетов и интерфейсов. Выделение процессов/сервисов допустимо только при доказанной необходимости по масштабированию, изоляции отказов или безопасности.

## 4. Ответственность слоёв

### 4.1. Control Plane

Control Plane отвечает на вопросы: какие кластеры находятся под управлением Kubron, кому они принадлежат, какие операции доступны и в каких пределах пользователь или автоматизация вправе действовать.

Capabilities:

- каталог кластеров, организаций и команд;
- явная идентичность кластера, независимая от активного UI-контекста;
- проверка принадлежности и полномочий перед каждой операцией;
- capability discovery: версия Kubernetes, API resources, provider type и доступность функций;
- пользовательские группы объектов, способные объединять ресурсы из разных кластеров;
- разрешение selector в конкретный, проверяемый набор целей;
- контекст выполнения, включающий actor, tenant, cluster и correlation ID.

**Группа целей не является механизмом выдачи прав.** Она только задаёт набор объектов. Доступ к каждому объекту всё равно ограничен tenant scope, app-RBAC и Kubernetes RBAC.

### 4.2. Operations Platform

Operations Platform владеет фактическими возможностями взаимодействия с Kubernetes и интеграциями:

- чтение и представление ресурсов;
- типизированные операции над ресурсами;
- Helm и GitOps workflows;
- Lifecycle: readiness, API/component compatibility, baseline и drift;
- предварительная проверка изменений;
- выполнение конкретных операций через контролируемые адаптеры;
- проверка наблюдаемого результата.

Каждая изменяющая операция должна быть описана типизированным контрактом. Произвольный shell, произвольный `kubectl` или строка команды не являются допустимым интерфейсом автономного исполнителя.

### 4.3. Intelligence Platform

Intelligence отвечает за понимание состояния и объяснение выводов:

- сбор доказательств через разрешённые источники;
- диагностика и построение гипотез;
- Dependency Graph и анализ области влияния;
- корреляция расследований и Problems;
- рекомендации с указанием оснований и ограничений;
- feedback по результатам расследований;
- оценка неопределённости и полноты покрытия.

Intelligence **не выдаёт разрешения на изменение кластера**. Высокая уверенность гипотезы не означает, что действие безопасно или разрешено. Intelligence поставляет факты, гипотезы и рекомендации; policy engine и исполнитель принимают отдельные решения.

### 4.4. Autonomy Layer

Autonomy отвечает за полный жизненный цикл управляемого действия:

- определение эффективного режима автономности;
- проверку политик и guardrails;
- построение типизированного плана;
- расчёт риска и blast radius;
- approval и привязку подтверждения к неизменяемому плану;
- координацию исполнения;
- идемпотентность и конкурентное владение запуском;
- проверку постусловий;
- разрешённые компенсирующие действия и recovery;
- полный audit trail.

Autonomy не должен дублировать Kubernetes client, credentials, tenant model или authz. Он использует существующую платформу и операции через узкие интерфейсы.

## 5. Общие контракты

Нужны общие **идентификаторы и гарантии**, но не универсальная JSON-модель для всех доменов.

### 5.1. Resource Identity

Минимальная устойчивая ссылка на Kubernetes-объект:

- Kubron `cluster_id`;
- API group/version и kind;
- namespace (если ресурс namespaced);
- name;
- Kubernetes UID, когда он доступен;
- resourceVersion — как маркер версии наблюдаемого состояния, не как долговременный идентификатор.

Имя объекта без cluster identity недостаточно: одинаковые namespace/kind/name могут существовать в разных кластерах.

### 5.2. Operation Context

Каждый запуск получает неизменяемый контекст:

- operation/run ID и correlation ID;
- инициатор: пользователь, расписание или системный trigger;
- organization/team scope;
- явный набор кластеров и объектов;
- причина или цель запуска;
- время создания и deadline;
- версия policy/profile;
- ссылки на evidence и план.

Идентификаторы tenant и кластера разрешаются сервером из каталога Kubron, а не принимаются как доказательство доступа из пользовательского payload.

### 5.3. Evidence Reference

Любой факт, используемый при принятии решения, должен иметь происхождение:

- источник (Kubernetes API, Events, metrics, GitOps, readiness, drift, Intelligence);
- объект/кластер, к которому относится факт;
- observedAt и, если возможно, resourceVersion;
- статус достоверности: known, unknown, partial или unavailable;
- coverage и причина пропуска данных;
- правила redaction и ссылка на сохранённое доказательство, если оно существует.

Устаревшее или неполное evidence не должно незаметно считаться актуальным. Для каждого класса действий определяется допустимый возраст доказательств.

### 5.4. Typed Action Contract

Каждое действие каталога должно задавать:

- стабильный action ID и версию контракта;
- допустимые типы целей;
- входные параметры с валидацией;
- необходимые permissions и Kubernetes verbs;
- риск-класс;
- preconditions;
- ожидаемые postconditions;
- оценку blast radius;
- стратегию verification;
- возможность и пределы recovery;
- требования к approval;
- идемпотентный ключ и поведение при повторе.

Каталог действий — allowlist. Неизвестный action ID, версия контракта или параметр означает отказ, а не попытку выполнить действие «как получится».

## 6. Модель автономности

### 6.1. Три режима

| Режим | Поведение | Изменение кластера |
|---|---|---|
| **Observe** | Наблюдает, анализирует, строит планы и показывает рекомендации | Запрещено |
| **Assisted** | Готовит план, показывает риск и последствия, ждёт явного approval | Только после требуемого подтверждения |
| **Autonomous** | Выполняет только действия, разрешённые эффективной политикой и guardrails | Разрешено в заданных пределах |

Режим задаётся на разных уровнях scope. Режим дочернего scope может только снижать автономность относительно родителя:

`Observe < Assisted < Autonomous`

Например, если организация установила `Observe`, кластер не может самостоятельно перейти в `Autonomous`. Если кластер находится в `Assisted`, отдельный workload не может расширить его полномочия.

### 6.2. Иерархия политик

Основная иерархия:

`Organization → Cluster → Namespace → Workload → Object → Action`

Политика может быть задана на любом уровне. Отсутствие дочерней политики означает наследование ограничений, а не расширение полномочий.

Правила вычисления эффективной политики:

1. Разрешённые действия — пересечение разрешений всех применимых уровней.
2. Запреты — объединение запретов; явный deny имеет приоритет.
3. Режим — минимальный уровень автономности среди применимых ограничений.
4. Лимиты риска, blast radius, частоты, времени и параллелизма — наиболее строгие применимые значения.
5. Требование approval не может быть снято дочерней политикой, если оно задано выше.
6. Неоднозначность, ошибка разрешения scope или отсутствие политики — fail-safe `Observe`.

### 6.3. Произвольные группы целей

Пользовательские группы дополняют иерархию и могут объединять объекты из разных кластеров. Например: «все frontend workloads тестовых кластеров» или «конкретные базы данных в выбранных production-кластерах».

Группа:

- хранит selector и владельца/tenant scope;
- имеет собственную версию;
- не предоставляет доступ к объектам;
- при запуске разрешается в явный набор Resource Identity;
- проходит policy evaluation отдельно для каждого объекта и кластера;
- ограничивается политиками всех родительских scope;
- сохраняет digest разрешённого набора целей в плане и истории операции.

Для интерактивного Assisted-сценария approval подтверждает конкретный snapshot целей. Если состав группы изменился, старый approval не распространяется на новые объекты.

Для Autonomous-сценария динамическая группа может разрешаться заново на каждом запуске, но новый snapshot обязан заново пройти все policy, risk и blast-radius checks. Превышение лимита целей блокирует запуск или требует отдельного approval.

### 6.4. Autonomy Profiles

Переиспользуемые профили — именованные наборы ограничений и поведения, например:

- `production-strict`;
- `development-full`;
- `database-protected`.

Профиль может задавать режим, allow/deny actions, risk ceiling, approval scope, временные окна, лимиты частоты и параллелизма, blast radius, preconditions, verification и recovery.

Профиль — шаблон политики, а не обход иерархии. Его применение не может расширить права, заданные Organization или Cluster.

### 6.5. Типы approval

Архитектура должна поддерживать три независимых механизма:

- **Per-action approval** — подтверждение отдельного действия или шага.
- **Policy-based automation** — заранее разрешённый набор действий в ограниченных условиях, без ручного подтверждения каждого запуска.
- **Goal-based operation** — пользователь задаёт желаемое состояние, Kubron строит план достижения цели, а все шаги проходят обычную policy evaluation.

Goal-based operation не означает свободное выполнение команд. Цель преобразуется в типизированный план из каталога разрешённых действий.

## 7. Жизненный цикл операции

Основной цикл:

```text
Observe
   ↓
Understand (evidence + Intelligence + Lifecycle)
   ↓
Decide (plan + risk + effective policy)
   ↓
Approve (если требуется)
   ↓
Execute (typed action + lease + idempotency)
   ↓
Verify (fresh reads + postconditions)
   ↓
Recover / Escalate
   ↓
Audit + Operation History
```

### 7.1. Plan

План — неизменяемый объект, содержащий:

- цель и scope;
- упорядоченные шаги и зависимости;
- конкретные targets;
- входные параметры;
- evidence и его свежесть;
- preconditions и postconditions;
- оценку риска, blast radius и лимиты;
- версию action catalog и policy;
- требования к approval;
- срок действия.

Любое изменение целей, параметров, последовательности шагов, policy revision или критичных preconditions создаёт новый план и требует повторной оценки/approval.

### 7.2. Approval

Подтверждение связывается не с текстовым описанием, а с полным digest плана, target snapshot, policy revision и expiry. При изменении любого из этих компонентов подтверждение становится недействительным.

Это продолжает уже используемый в Lifecycle принцип: preview/confirmation должны быть привязаны к полному состоянию, которое пользователь видел и подтверждал.

### 7.3. Execute

Исполнение выполняется только через typed action adapters. Перед каждым шагом повторно проверяются:

- tenant и app-RBAC;
- доступность кластера и актуальные Kubernetes permissions;
- эффективная политика и режим;
- срок действия approval;
- preconditions и актуальность target;
- лимиты параллелизма и blast radius.

### 7.4. Concurrency и идемпотентность

Для пользовательских и автоматических запусков нужен долговременный журнал операций и атомарные переходы состояний.

Рекомендуемая модель:

- устойчивый run ID и idempotency key;
- атомарный claim запуска;
- lease с владельцем, expiry и fencing token;
- повторная проверка preconditions после получения lease;
- запись результата каждого шага;
- безопасный retry только для действий с определённой семантикой повторения;
- восстановление незавершённых запусков после рестарта/потери реплики.

Нельзя обещать exactly-once для внешнего Kubernetes API. Целевая семантика — at-least-once доставка/попытка с идемпотентными обработчиками, проверкой фактического состояния и reconciliation. Повторный запуск не должен слепо повторять side effect.

### 7.5. Verification и recovery

Успех означает, что postconditions подтверждены свежим чтением, а не только то, что Kubernetes API принял запрос.

Результаты проверки должны различать:

- подтверждено;
- не подтверждено;
- неизвестно из-за отсутствия доступа/данных;
- частично выполнено;
- проверка не завершена по deadline.

Recovery не равен универсальному rollback. Для каждого action явно описывается, существует ли безопасная компенсирующая операция, при каких условиях она допустима и как проверяется. Если безопасного восстановления нет, операция останавливается и эскалируется человеку.

### 7.6. Несколько кластеров

Группа из нескольких кластеров не образует распределённую транзакцию. Запуск разбивается на независимые cluster-scoped sub-runs с общим parent run.

План обязан задавать стратегию:

- последовательное или ограниченно-параллельное исполнение;
- размер волны;
- остановку после ошибки;
- поведение при частичном успехе;
- условия продолжения следующей волны;
- отдельную проверку результата каждого кластера.

Статус общего запуска агрегируется из sub-runs и не скрывает частичные результаты.

## 8. Безопасность и guardrails

Обязательные инварианты:

1. **Observe по умолчанию.** Отсутствие или неоднозначность политики никогда не включает запись.
2. **Least privilege.** App-RBAC и Kubernetes RBAC проверяются независимо; одно не заменяет другое.
3. **No bypass.** Все обращения проходят существующие credentials, `ConfigFor`, tenant и cluster access path.
4. **Typed actions only.** Нет произвольного shell, произвольного kubectl или AI-generated command execution.
5. **Explicit approval.** Подтверждение связано с неизменяемым планом, scope и сроком.
6. **Fresh preconditions.** Перед исполнением проверяется, что состояние не изменилось с момента планирования.
7. **Blast-radius limits.** Ограничения по объектам, namespace, кластерам, параллелизму и числу шагов.
8. **Rate/action budgets.** Ограничения на частоту и совокупный объём действий в заданном окне.
9. **Time windows.** Запрет исполнения вне разрешённых окон и при истёкшем deadline.
10. **Auditability.** Записываются субъект/trigger, policy decision, plan digest, approvals, шаги, результат проверки и recovery; секреты и чувствительные значения не попадают в аудит.
11. **Fail closed.** Ошибка policy engine, Store, lease, authz или verification не трактуется как разрешение.
12. **No hidden cluster installation.** Автономность не требует обязательного агента, CRD или брокера в пользовательском кластере.

### AI boundary

AI может быть необязательным помощником для суммаризации evidence, объяснения и подготовки черновика цели/плана. Он не является policy engine, не подтверждает права, не классифицирует риск как единственный источник истины и не получает прямой доступ к Kubernetes API.

Любой предложенный AI шаг преобразуется в typed action, проходит детерминированную валидацию и обычную policy evaluation. Внешняя передача данных остаётся выключенной по умолчанию и подчиняется отдельной настройке и правилам редактирования.

## 9. Интеграция существующих доменов

| Существующий домен | Роль в целевом цикле |
|---|---|
| Cluster Manager / Credentials | Устанавливает безопасный контекст подключения и идентичность кластера |
| Ops Platform | Предоставляет контролируемые источники чтения и лимиты сбора |
| Intelligence | Даёт evidence, гипотезы, корреляцию, область влияния и рекомендации |
| Readiness | Может выступать precondition/gate для maintenance-плана |
| Baseline / Drift | Даёт проверяемое состояние конфигурации и ограничения перед/после изменения |
| Helm / Argo CD / Flux | Выполняют собственные типизированные workflows; Kubron не подменяет reconcile контроллера |
| Audit / Store / Events | Обеспечивают сохранение истории, контроль доступа и уведомление UI |

Примеры взаимодействия:

- Intelligence обнаружил деградацию нескольких workloads → построил гипотезы и область влияния → Autonomy предлагает план диагностики или безопасного действия.
- Lifecycle сообщает о несовместимом API → maintenance plan блокируется или требует отдельного approval.
- Drift показывает изменение критичного поля → политика запрещает автоматическое исправление или требует подтверждения владельца.
- После действия Operations выполняет свежую проверку → Intelligence обновляет evidence, а Autonomy закрывает run только после подтверждения postconditions.

Ни один домен не должен напрямую менять внутреннее состояние другого. Связь строится через публичные доменные интерфейсы и ссылки на результаты.

## 10. Целевые границы пакетов

Это предварительные границы ответственности, а не приказ немедленно создать перечисленные пакеты:

| Область | Текущие пакеты | Целевая ответственность |
|---|---|---|
| Foundation | `tenant`, `auth`, `credential`, `store`, `pgstore`, `audit`, `jobs`, `replicaevents` | Общие инфраструктурные гарантии |
| Control Plane | `app`, `teams`, `tenant`, `credential`, cluster manager | Fleet catalog, target groups, explicit scope resolution |
| Operations | `k8s`, `opsplatform`, `readiness`, `baseline`, `drift` | Read/write capabilities и typed adapters |
| Intelligence | `diagnose`, `depgraph`, `signals`, `correlation`, `incident`, `feedback` | Evidence и объяснимые выводы |
| Autonomy (новая область) | пока отсутствует | Policy evaluation, plans, approvals, run orchestration, verification, recovery |

Новые пакеты не должны импортировать `internal/app` или `internal/server` как способ получить инфраструктуру. Слои приложения связывают доменные сервисы через интерфейсы. Конкретный граф импортов и API каждого пакета будет определён в отдельном design pass до реализации.

## 11. Этапы реализации

Архитектуру уровня 3 проектируем сразу, но реализацию разбиваем на независимые этапы с критериями выхода.

### Этап 0. Architecture Baseline — текущий

Результат:

- целевая модель A+B+C и Autonomy;
- карта существующих возможностей и ограничений;
- общие контракты;
- политика автономности и модель scope;
- жизненный цикл плана/исполнения;
- список ADR и критерии перехода к реализации.

**Выход:** согласованная архитектура без production-изменений.

### Этап 1. Shared Operation Contracts

Спроектировать и затем реализовать только общие контракты:

- explicit operation context и resource identity;
- target groups и безопасное разрешение scope;
- evidence references и freshness;
- typed action catalog;
- общие risk/coverage/precondition модели.

**Выход:** домены могут обмениваться ссылками и контрактами без прямой зависимости друг от друга. Изменяющие операции пока не запускаются автоматически.

### Этап 2. Assisted Operations

Ограниченный набор действий с явным подтверждением:

- immutable plan и preview;
- policy evaluation в режиме Observe/Assisted;
- approval, привязанный к digest плана;
- durable run state и audit;
- execution одного кластера;
- verification и безопасная обработка частичного результата.

Начать с небольшой группы обратимых и хорошо проверяемых действий. Состав action catalog определяется отдельным анализом риска; не открывать весь существующий набор операций сразу.

**Выход:** пользователь видит, что будет сделано, явно подтверждает неизменяемый план, а Kubron доказывает результат.

### Этап 3. Policy-based Autonomy

Добавить:

- иерархические политики;
- Autonomy Profiles;
- режим Autonomous для ограниченных action types и scopes;
- расписания/триггеры;
- leases, fencing, идемпотентность и восстановление незавершённых запусков;
- бюджеты, лимиты, окна и blast-radius guards.

Начальные профили и разрешённые действия должны быть консервативными. Autonomous не включается глобально по умолчанию.

**Выход:** узкие сценарии выполняются без ручного approval только при полном совпадении условий политики.

### Этап 4. Cross-cluster Orchestration

Добавить:

- произвольные группы целей из нескольких кластеров;
- parent run и cluster-scoped sub-runs;
- волны и ограниченный параллелизм;
- остановку и продолжение по политике;
- агрегированную отчётность с явной частичной успешностью.

**Выход:** безопасное выполнение согласованных операций на нескольких кластерах без ложного обещания атомарности.

### Этап 5. Goal-based Operations

Добавить декларативные цели:

- типизированные goal contracts;
- преобразование цели в план;
- проверку достижимости и конфликтов;
- повторную оценку состояния и convergence loop;
- ограничения числа итераций, времени и расхода action budget;
- approval/policy gate для каждого нового плана.

**Выход:** Kubron может поддерживать заданное пользователем целевое состояние, но каждое изменение остаётся объяснимым, ограниченным и проверяемым.

### Этап 6. Recovery Maturity

Расширить recovery только для действий с доказуемо безопасной компенсирующей операцией:

- recovery plans;
- проверка возможности компенсации;
- остановка при неопределённом состоянии;
- ручное продолжение после эскалации;
- тесты отказов, рестартов и гонок.

**Выход:** система корректно переживает сбои и частичные операции, не маскируя неопределённость под успех.

## 12. Предлагаемая последовательность ADR

Новые решения должны дополнять существующие ADR; реализованные ADR-0001…0034 не переписываются.

| Предлагаемый ADR | Тема | Что необходимо решить |
|---|---|---|
| ADR-0035 | Kubron Platform Architecture | Слои A+B+C, зависимости и границы доменов |
| ADR-0036 | Operation Context and Target Groups | Явный scope, группы, identity и разрешение целей |
| ADR-0037 | Typed Action Catalog and Risk Model | Контракт действия, risk classes, pre/postconditions |
| ADR-0038 | Autonomy Policy and Profiles | Иерархия политик, режимы, наследование, fail-safe |
| ADR-0039 | Plans and Approvals | Immutable plan, digest, expiry, per-action/plan approval |
| ADR-0040 | Durable Operation Execution | Run state, leases, fencing, idempotency, retries, HA |
| ADR-0041 | Verification and Recovery | Postconditions, неизвестный результат, компенсации |
| ADR-0042 | Cross-cluster Orchestration | Группы, waves, partial success, blast radius |
| ADR-0043 | Goal-based Operations | Goal contracts, planning, convergence и лимиты |

Это предварительный список. Нумерацию и содержание следует утвердить после архитектурного review, а не создавать все ADR формально заранее.

## 13. Что сознательно не проектируем как обязательную часть

- Микросервисную декомпозицию и отдельный control-plane deployment.
- Обязательный агент, CRD или operator в каждом кластере.
- Обязательный message broker или внешнюю очередь.
- Произвольное выполнение shell/kubectl.
- Автоматическое исправление любого finding.
- AI как источник прав, policy decisions или единственный механизм диагностики.
- Универсальную схему хранения всех доменных объектов.
- Глобальный Autonomous mode, включённый по умолчанию.

Каждый из этих вариантов может вернуться на рассмотрение только при конкретном доказанном требовании.

## 14. Критерии архитектурной готовности к реализации

До первого runtime-изменения должны быть согласованы:

- [ ] Границы Control Plane, Operations, Intelligence, Autonomy и Foundation.
- [ ] Контракт Resource Identity и Operation Context.
- [ ] Модель target groups и правила межкластерного scope resolution.
- [ ] Иерархия политик, deny semantics и fail-safe поведение.
- [ ] Семантика Observe, Assisted и Autonomous.
- [ ] Каталог первых typed actions и их risk classification.
- [ ] Модель immutable plan и approval binding.
- [ ] Долговременное состояние запуска, lease/fencing и idempotency.
- [ ] Семантика verification, partial success и recovery.
- [ ] Модель аудита, retention, privacy и redaction.
- [ ] Совместимость desktop, single-replica и HA server.
- [ ] Набор fault-injection и concurrency tests для критических переходов.

## 15. Архитектурные инварианты Kubron

1. Kubron остаётся одной платформой, а не набором несвязанных продуктов.
2. Control Plane не подменяет Kubernetes API server и не управляет им напрямую.
3. Operations выполняет только явно описанные и разрешённые действия.
4. Intelligence объясняет и рекомендует, но не выдаёт полномочия.
5. Autonomy не обходит authz, tenant isolation, Kubernetes RBAC и аудит.
6. Ни один approval не действует на изменившийся план или новый набор целей.
7. Ни один неизвестный результат не объявляется успешным.
8. Межкластерная операция не маскирует частичный успех под атомарный.
9. Неопределённость всегда уменьшает автономность, а не увеличивает её.
10. Существующие домены сохраняют собственные модели и хранилища.
11. Архитектура остаётся пригодной для desktop и server/HA.
12. Развитие идёт от Observe к Assisted и затем к ограниченному Autonomous, без скачка сразу к полной автоматизации.
