# Kubron Intelligence: расследования (ADR-0024)

Раздел **Incidents** диагностирует workload без изменения кластера и без AI. Он отвечает на вопрос «почему Pod или Deployment не работает» и показывает, **на чём основан ответ**.

## Что делает расследование

Расследование открывается для Pod, Deployment или ReplicaSet. Kubron читает только чтением (`get`/`list`) Pod, `pods/log`, Events, ReplicaSet, Deployment, Namespace и Node. **Secret не читается и в allowlist платформы его нет.** Правила версионируются (`RuleSetVersion`, сейчас 1) и покрывают:

| Симптом | Что проверяется |
|---|---|
| Pod в Pending | условие `PodScheduled`, события `FailedScheduling`: нехватка ресурсов, nodeSelector/affinity, taint, PVC |
| CrashLoopBackOff | код и причина последнего завершения, перезапуски, события BackOff и Unhealthy (liveness) |
| OOMKilled | лимит памяти контейнера, давление памяти на узле |
| Ошибки запуска | ImagePullBackOff, ErrImagePull, InvalidImageName, CreateContainerConfigError, RunContainerError, тома |
| Выкат Deployment/ReplicaSet | ProgressDeadlineExceeded, ReplicaFailure, квота, отказ admission, пауза, неготовые Pod нового ReplicaSet |

Отчёт состоит из **разных типов записей**, их нельзя спутать ни в данных, ни в интерфейсе:

- **факт** — наблюдение с источником (поле объекта, событие, лог) и временем получения;
- **гипотеза** — предположение с уверенностью `low`/`medium`/`high`, подтверждающими и противоречащими фактами. Значения «установлено» нет: гипотеза **никогда** не становится установленной причиной сама. Подтвердить её может только человек, когда отмечает результат расследования;
- **рекомендация** — предлагаемое изменение. Kubron его не выполняет;
- **диагностический шаг** — что ещё проверить (только чтение);
- **недостающий контекст** — чего не хватило правилу (недоступный источник, усечённый список событий, нет данных). Правила защитные: нехватка данных — это запись в отчёте, а не ошибка и не паника.

## События и логи как доказательства

- **Events** собираются при открытии расследования и обновляются кнопкой **Update Events**, пока расследование открыто (фонового наблюдателя нет). Снимок хранится в инциденте: события недолговечны в кластере. До 200 событий.
- **Фрагменты логов** — ограниченные куски лога вокруг якорной строки (последняя строка с признаком ошибки). Сохраняются автоматически только те, на которые ссылается finding; остальное — кнопкой **Save as evidence**.

Пределы заданы в коде и не настраиваются:

| Предел | Значение |
|---|---|
| строк на фрагмент | 200 |
| байт на фрагмент (после редакции) | 32 КиБ |
| длина строки | 2 КиБ (длиннее усекается) |
| фрагментов на расследование | 10 |
| байт фрагментов на расследование | 256 КиБ |

Перед записью текст проходит редактор (ADR-0022, `internal/logredact`). Он **fail-closed**: при любой ошибке редактора, не-UTF-8 или бинарном входе, превышении лимита фрагмент **не сохраняется**, а finding получает пометку «доказательство не сохранено» и причину (`redaction_failed`, `not_text`, `limit_exceeded`, `incident_quota`, `log_unavailable`, `empty_log`, `disabled_*`, `deleted`). Тексты Events и сообщения отчёта редактируются так же; при сбое редактора вместо текста сохраняется заменитель `[unavailable]`, а не оригинал.

В записи фрагмента: кластер, namespace, pod, container, экземпляр (текущий или предыдущий), время получения и интервал строк, признак усечения, версия редактора, число замен, SHA-256 редактированного текста и сам текст. В server текст дополнительно шифруется ключами из `KUBRON_SECRET_KEY` (ADR-0008, таблица `incident_fragments`, входит в `kubron-server rekey` и проверку ключей при старте). В desktop — файлы `0600` в каталоге данных.

Фрагменты **не передаются во внешний AI** (AI в этой версии нет совсем) и **не входят в экспорт по умолчанию**.

## Права

| Действие | Право |
|---|---|
| открыть, обновить Events, смотреть историю и отчёт, отметить результат, сохранить фрагмент, отключить сохранение для расследования | `read` |
| **прочитать содержимое** сохранённого фрагмента; включить фрагменты в экспорт | `diagnostics.logs` |
| удалить фрагмент, удалить расследование, удалить уже сохранённые фрагменты | `diagnostics.logs` |
| изменить настройки хранения | `users.manage` (администратор) |

`diagnostics.logs` по умолчанию есть у ролей `admin` и `operator`, у `user` его нет. Право проверяется на сервере при **каждом** чтении содержимого. Без права видны метаданные фрагмента (контейнер, время, число строк), а вместо текста — «содержимое скрыто». Живой просмотр логов по-прежнему требует только `read`. Чтение фрагментов и экспорт пишутся в журнал аудита (кто, кластер, инцидент, число фрагментов) **без содержимого**.

## Хранение и настройки

- фрагменты — не дольше **15 дней** (значение по умолчанию и верхняя граница; настраивается только в сторону сокращения, 1–15);
- расследования — **90 дней** по умолчанию, настраивается до **365** (отсчёт — от последней активности);
- выключатель «не сохранять фрагменты логов» (организация в server, приложение в desktop) и список namespace-исключений (по умолчанию пуст);
- расследование можно запретить сохранять логи и удалить уже сохранённые фрагменты; удаление расследования удаляет его фрагменты.

Просроченное удаляет периодическая задача (`internal/jobs`; в server её выполняет одна реплика, `pg_try_advisory_lock`).

Значения по умолчанию для организаций, у которых настройки не сохранены в интерфейсе:

| Переменная | Значение |
|---|---|
| `KUBRON_INCIDENT_LOG_EVIDENCE` | `on` (по умолчанию) или `off` |
| `KUBRON_INCIDENT_FRAGMENT_RETENTION_DAYS` | 1–15, по умолчанию 15 |
| `KUBRON_INCIDENT_RETENTION_DAYS` | 1–365, по умолчанию 90 |
| `KUBRON_INCIDENT_EXCLUDED_NAMESPACES` | список через запятую, по умолчанию пуст |
| `KUBRON_INCIDENT_PURGE_INTERVAL` | период задачи очистки, по умолчанию `1h`, не меньше `1m` |

Неверное значение — ошибка запуска сервера (в desktop расследования отключаются, остальное работает).

## Устройство

`internal/diagnose` (сбор контекста и правила, без хранилища), `internal/incident` (модель, `Backend`, сервис, фрагменты, retention, файловое хранилище), `internal/pgstore/incidents.go` (PostgreSQL, миграция `0011_incidents`), слой связки `internal/app/app_incident.go` (методы `Incident*`: `Provider.Begin`, аудит, события). Один набор контрактных тестов `internal/incident/incidenttest` запускается против обеих реализаций хранилища.
