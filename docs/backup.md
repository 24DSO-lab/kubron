# Резервное копирование и восстановление

Сервисный режим (PostgreSQL) хранит состояние в двух частях, и **их нужно копировать и хранить раздельно**:

| Что | Где лежит | Как копировать |
| --- | --- | --- |
| Пользователи, команды, метаданные кластеров, журнал аудита, состояние Helm, веб-сессии, **зашифрованные** kubeconfig и секреты | БД PostgreSQL | `pg_dump` или снимки хранилища |
| Ключ шифрования секретов `KUBRON_SECRET_KEY` (и прежние ключи) | Secret / менеджер секретов | Копия в менеджере паролей или KMS, не рядом с копией БД |

Дамп БД без ключа бесполезен для секретов: kubeconfig и пароли кластеров, токены Argo CD и секреты
репозиториев Helm расшифровать нельзя. Ключ без дампа бесполезен тем более. Поэтому копия ключа, лежащая рядом
с копией БД (в одном хранилище, с тем же доступом), лишает шифрование смысла. Чарт ключ **не генерирует**:
потеря ключа означает потерю всех секретов в БД, а восстановить их можно только добавив кластеры заново.

## Резервное копирование

**БД.** Формат custom (`-Fc`) позволяет выборочное и параллельное восстановление:

```bash
pg_dump -Fc --no-owner --no-privileges -f kubron-$(date +%F).dump "$KUBRON_DATABASE_URL"
```

- Периодичность определяет допустимая потеря данных: для журнала аудита и составов команд обычно достаточно
  ежедневной копии плюс WAL-архив или PITR средствами вашей СУБД или облака.
- Копии БД шифруйте на диске и в передаче; доступ к ним у узкого круга людей. Они содержат хеши паролей,
  журнал аудита и шифротексты секретов.
- Веб-сессии (`web_sessions`) для восстановления не нужны: после него пользователи просто войдут заново. Если не
  хотите переносить их в тестовую среду, очистите: `TRUNCATE web_sessions;`.
- Пример CronJob с `pg_dump` в объектное хранилище — на стороне вашей инфраструктуры; чарт его не создаёт.

**Ключ.** Менеджер паролей, KMS или запечатанный конверт, доступ у узкого круга людей. Храните:

- сам ключ вида `id:base64` и его `id`;
- **все прежние ключи, пока существуют копии БД, сделанные до их замены** (см. «Ротация ключа»): копия БД
  читается теми ключами, которыми были зашифрованы её записи.

Узнать, какие `id` ключей нужны данным в БД:

```sql
SELECT key_id, count(*) FROM clusters WHERE kubeconfig_enc IS NOT NULL GROUP BY key_id;
SELECT secret_key_id, count(*) FROM clusters WHERE secret_enc IS NOT NULL GROUP BY secret_key_id;
```

Записывайте `id` текущего ключа рядом с каждой копией БД (например, в имени файла): так при восстановлении
сразу видно, какой ключ достать.

## Восстановление

1. Создайте пустую БД и восстановите дамп:
   ```bash
   createdb kubron
   pg_restore --no-owner --no-privileges --exit-on-error -d kubron kubron-2026-11-01.dump
   ```
2. Создайте Secret с **тем же ключом** (тот же `id` и те же байты) и, если в дампе остались записи под
   прежними ключами, добавьте их в `KUBRON_SECRET_KEY_PREVIOUS` (через запятую).
3. Установите чарт (или запустите сервер) с `KUBRON_DATABASE_URL`, указывающим на восстановленную БД. Миграции
   применятся сами, если дамп сделан на более старой схеме.
4. Проверьте: `/healthz` и `/readyz` отвечают `200`, вход под известной учётной записью проходит, кластер команды
   открывается.

Сервер при старте читает по одной зашифрованной записи на каждый `id` ключа и **не стартует**, если ключа нет или
он не подходит. Ошибка называет причину и этот документ:

| Сообщение | Причина | Что делать |
| --- | --- | --- |
| `…KUBRON_SECRET_KEY does not match…: …stored with encryption key "k1"…: ciphertext was encrypted with an unknown key` | В связке нет ключа с таким `id` | Добавьте ключ `k1` в `KUBRON_SECRET_KEY` (если он был текущим) или в `KUBRON_SECRET_KEY_PREVIOUS` |
| `…: failed to decrypt the secret` | `id` совпал, а байты ключа другие (ключ из другого окружения, опечатка) | Возьмите ключ, которым шифровались данные этой БД |

Текст ошибки не содержит ключа и расшифрованных данных. При выкладке с `RollingUpdate` реплика с неверным ключом не
станет готовой, а старые реплики продолжат работать.

Если ключ утерян безвозвратно, а БД нужна (например, выгрузить журнал аудита), запустите сервер с
`KUBRON_ALLOW_KEY_MISMATCH=1`: он стартует, пользователи и команды работают, а секреты кластеров недоступны.
После этого добавьте кластеры заново (`UpdateCluster` с новым kubeconfig). Постоянно держать этот режим включённым не
следует.

## Ротация ключа и `rekey`

Новые записи шифруются текущим ключом, старые читаются прежними, пока не будут перешифрованы.

1. Создайте новый ключ с **новым `id`** (формат `id:base64`, 32 байта):
   ```bash
   echo "2026-11:$(openssl rand -base64 32)"
   ```
   Сохраните его в менеджере секретов **до** использования.
2. В Secret: новый ключ в записи `KUBRON_SECRET_KEY`, прежний в записи `KUBRON_SECRET_KEY_PREVIOUS` (через запятую,
   если прежних несколько). В чарте `secrets.keys.*` задают только **имена** записей внутри Secret; чтобы сервер читал
   прежний ключ, задайте `secrets.keys.previousSecretKey: KUBRON_SECRET_KEY_PREVIOUS` (по умолчанию пусто). Перезапустите
   все реплики (`kubectl rollout restart deploy/kubron`). Сервер стартует: связка читает данные обоими ключами.
3. Перешифруйте записи новым ключом. Команда читает БД из окружения сервера, поэтому запускайте её там, где оно есть:
   ```bash
   kubectl exec deploy/kubron -- /kubron-server rekey
   # re-encrypted with key "2026-11": 12 kubeconfigs, 3 cluster secrets, 2 Argo CD tokens, 4 Helm repository secrets, 5 sign-in credentials (0 still in legacy format)
   ```
   `rekey` повторяется безопасно: уже перешифрованные записи пропускаются, и повторный запуск ничего не меняет.
   В образе нет оболочки, поэтому команда запускается напрямую, либо одноразовым Job с теми же переменными окружения.
4. Убедитесь, что старый `id` больше не нужен: запросы из раздела «Резервное копирование» показывают только новый
   `key_id`.
5. Прежний ключ из `KUBRON_SECRET_KEY_PREVIOUS` можно убрать, но **храните его, пока живут копии БД, сделанные до
   `rekey`**: их записи зашифрованы им. Срок хранения ключа равен сроку хранения самой старой копии, которую вы
   захотите уметь восстановить.

`rekey` перешифровывает kubeconfig'и, секреты подключения кластеров, токены Argo CD и секреты репозиториев Helm.
Ключ меняйте по расписанию (например, раз в год) и при подозрении на компрометацию. Если ключ скомпрометирован,
после `rekey` замените и сами секреты кластеров (токены, пароли): копии БД старее ротации остаются расшифровываемыми
старым ключом.

## Проверка

Восстановление проверяется автоматически: job `restore-check` в CI выполняет `scripts/restore-check.sh`.

1. Сервер на БД `src` с ключом K1: администратор, команда, пользователь и кластер с секретом (токен в kubeconfig).
2. `pg_dump` работающего сервера, восстановление в пустую БД `dst`.
3. Сервер на `dst` с тем же ключом K1 и пустым каталогом данных: вход проходит, kubeconfig читается и **совпадает
   с исходным**.
4. Неверный ключ (другой `id`; тот же `id` с другими байтами): сервер не стартует, ошибка понятная, ключа в ней нет.
5. `KUBRON_ALLOW_KEY_MISMATCH=1`: сервер стартует, секрет не отдаётся.
6. Ротация: новый ключ плюс прежний → `rekey` → сервер только с новым ключом читает тот же секрет.
7. В журналах сервера нет токена и байтов ключей.

Запуск вручную (нужны PostgreSQL, `pg_dump`, `pg_restore`, `psql`, `curl`, `jq`, `openssl`):

```bash
go build -o kubron-server ./cmd/kubron-server
PGHOST=127.0.0.1 PGUSER=postgres PGPASSWORD=postgres KUBRON_SERVER_BIN=./kubron-server scripts/restore-check.sh
```

Скрипт создаёт и удаляет базы `kubron_restore_src` и `kubron_restore_dst`.

Для эксплуатации этого мало: **раз в квартал** восстанавливайте последнюю настоящую копию на отдельном сервере с
ключом из вашего менеджера секретов и проверяйте вход и доступ к кластеру. Только так видно, что копия и ключ
действительно хранятся и сочетаются.

## Режим одного пользователя и десктоп

Без PostgreSQL данные лежат в каталоге данных (`~/.kubron` или `KUBRON_DATA_DIR`): копируйте каталог целиком, как и
раньше. Этот документ относится к режиму с PostgreSQL.
