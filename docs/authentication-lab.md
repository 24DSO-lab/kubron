# Ручная лаборатория авторизации облачных кластеров

Этот стенд нужен, чтобы пройти сценарии входа в **десктопном Kubron** и увидеть интерфейс авторизации, не создавая EKS/GKE/AKS-кластеры.

Стенд создаёт три kubeconfig с закрытым адресом Kubernetes API `https://127.0.0.1:1`. Это намеренно: Kubron должен получить credentials, после чего ожидаемо не сможет подключиться к API. Успешная авторизация и доступность Kubernetes API — разные проверки.

> Скрипт не создаёт облачные ресурсы, не получает и не сохраняет секреты. Он только генерирует kubeconfig-файлы. Не добавляйте в них реальные токены или ключи.

## 1. Подготовка

Нужны только те CLI, чей сценарий вы хотите пройти:

- AWS: AWS CLI v2; для SSO заранее выполните `aws sso login --profile <profile>`.
- GKE: Google Cloud CLI и компонент `gke-gcloud-auth-plugin`; для ADC выполните `gcloud auth application-default login`.
- AKS: Azure `kubelogin`; для device-code входа потребуется доступ к Microsoft Entra ID.

Запустите генератор из корня репозитория:

```bash
bash scripts/auth-lab/generate-kubeconfigs.sh
```

Необязательные параметры:

```bash
EKS_CLUSTER_NAME=kubron-demo \
AWS_REGION=eu-west-1 \
AWS_PROFILE=kubron-sso \
AKS_TENANT_ID=<tenant-guid> \
KUBRON_AUTH_LAB_DIR=.kubron-auth-lab \
  bash scripts/auth-lab/generate-kubeconfigs.sh
```

`EKS_CLUSTER_NAME` здесь — только имя, включаемое в подписанный запрос EKS. Самого кластера с таким именем создавать не нужно. Регион и профиль должны соответствовать вашей AWS-конфигурации. `AKS_TENANT_ID` можно не задавать, если `kubelogin` может определить tenant из текущей Azure-конфигурации.

## 2. Запуск сценариев в Kubron

1. Соберите/запустите desktop-приложение из этой ветки: `wails dev`.
2. Добавьте каждый из трёх kubeconfig как отдельное подключение через обычный экран добавления кластера.
3. Для каждого подключения нажмите «Подключиться».
4. Подтвердите запуск exec-плагина, если Kubron покажет диалог подтверждения. Внимательно проверьте команду и аргументы.
5. Пройдите вход в соответствующем CLI/IdP.
6. После получения credentials ожидайте ошибку подключения к Kubernetes API: адрес намеренно указывает на закрытый локальный порт.

### EKS

Файл: `.kubron-auth-lab/eks.kubeconfig`.

При наличии AWS CLI Kubron запускает `aws eks get-token` после подтверждения. Для AWS IAM Identity Center сначала выполните `aws sso login --profile <profile>` в терминале; затем повторите подключение в Kubron. Само получение EKS token не требует существующего EKS control plane, но требует действительных AWS credentials и корректных имени кластера/региона для формирования токена.

### GKE

Файл: `.kubron-auth-lab/gke.kubeconfig`.

Плагин использует Application Default Credentials. Выполните `gcloud auth application-default login` в терминале до подключения. Kubron должен запросить подтверждение запуска `gke-gcloud-auth-plugin`, затем получить ExecCredential. Это проверяет путь CLI/ADC; это **не** проверка нативного Google OAuth-диалога Kubron.

### AKS

Файл: `.kubron-auth-lab/aks.kubeconfig`.

Плагин запускается с `--login devicecode`. Проверьте, как Kubron показывает подтверждение exec и результат работы `kubelogin`. Если device-code требует интерактивный терминал, этот сценарий может завершиться ограничением текущей реализации запуска exec-плагинов: зафиксируйте фактический текст/поведение, не вводите код в случайное окно и не обходите предупреждение о запуске команды.

## 3. Чек-лист визуальной проверки

Для каждого провайдера отметьте:

- [ ] В карточке/списке отображается правильное имя тестового подключения.
- [ ] При подключении появляется ожидаемый диалог подтверждения exec.
- [ ] В команде и аргументах нет неожиданных параметров или секретов.
- [ ] Значения переменных окружения не раскрываются в интерфейсе.
- [ ] Отмена диалога действительно отменяет запуск.
- [ ] При успешном получении ExecCredential диалог авторизации закрывается.
- [ ] После этого отображается отдельная ошибка недоступного Kubernetes API.
- [ ] Повторное подключение ведёт себя предсказуемо; истёкшие credentials требуют повторного входа.

Для проверки негативного сценария можно временно указать несуществующий executable в тестовом kubeconfig и повторить подключение: ожидается понятная ошибка запуска плагина. Не изменяйте kubeconfig рабочего кластера.

## 4. Что этот стенд не проверяет

- Принятие токена реальным EKS/GKE/AKS API Server.
- Kubernetes RBAC и права пользователя в кластере.
- Нативные формы AWS/GKE/Azure, если приложение не направляет конкретный kubeconfig на соответствующий нативный provider.
- Веб-сценарий: в веб-версии произвольные exec-плагины не запускаются на сервере.

## 5. Очистка

Удалите созданные тестовые подключения из Kubron и каталог `.kubron-auth-lab`. Выход из AWS SSO, Google ADC и Microsoft Entra выполняйте штатными средствами соответствующих CLI. Удаление kubeconfig не отзывает cloud credentials.
