# Журнал процесса и аудит в stdout

## Журнал процесса

Сервер пишет структурированный журнал (`log/slog`) в **stderr**, по одной JSON-записи на строку:

```json
{"time":"2026-11-01T10:00:00.123Z","level":"ERROR","msg":"rpc call failed","method":"GetPods","error":"...","request_id":"3f9c1a7e5b2d4c80"}
```

| Переменная | Значения | По умолчанию |
| --- | --- | --- |
| `KUBRON_LOG_LEVEL` | `debug`, `info`, `warn`, `error` | `info` |
| `KUBRON_LOG_FORMAT` | `json`, `text` (читаемый вывод для разработки) | `json` |

В чарте: `kubron.logLevel`, `kubron.logFormat`. Неверное значение — сервер не запускается.

Старый код, который ещё пишет через `log.Printf`, тоже выходит JSON-ом (стандартный `log` перенаправлен
в `slog`), без поля `request_id`.

## Идентификатор запроса

Каждый HTTP-запрос получает идентификатор; записи журнала, сделанные в его обработке, несут поле
`request_id`. Он же возвращается в заголовке ответа `X-Request-Id`, поэтому пользователь может назвать
его при обращении в поддержку, а администратор найти все записи запроса.

Если запрос уже пришёл с `X-Request-Id` (ingress-nginx, Envoy), он принимается при условии, что состоит
из 8–64 символов `A–Z a–z 0–9 . _ -`. Иначе (слишком длинный, с пробелами, переводами строк, кавычками)
создаётся новый: так заголовком нельзя подделать запись журнала.

## Секреты в журнале

Журнал не должен содержать секретов, и код их туда не передаёт. Дополнительно каждая запись (сообщение
и все атрибуты, включая тексты ошибок) проходит через редактор, который заменяет на `[REDACTED]`:

- значения атрибутов с именами, содержащими `password`, `secret`, `token`, `authorization`, `cookie`,
  `kubeconfig`, `apikey`, `databaseurl`, `dsn`, `credential`, `csrf`;
- заголовки `Authorization: Bearer …` / `Basic …`, пары `password=…`, `token: …`, `client_secret=…`;
- пароль в адресах `scheme://user:password@host`: пользователь и хост остаются для диагностики;
- JWT и закрытые ключи PEM;
- значения, известные серверу: `KUBRON_SECRET_KEY` (и прежние ключи) и пароли из `KUBRON_DATABASE_URL`,
  `KUBRON_DB_LISTEN_URL`.

Редактор — страховка на случай, когда секрет попал в чужое сообщение об ошибке (драйвер БД, клиент
кластера, OIDC-провайдер). Он может скрыть и безобидный текст вида `token: expired`; это сознательный выбор
в пользу безопасности. Тесты: `internal/logging`, `internal/server/requestid_test.go`.

## Аудит в stdout

`KUBRON_AUDIT_STDOUT=1` (чарт: `kubron.auditStdout=true`) дублирует каждую запись журнала аудита строкой
JSON в **stdout**. Журнал в БД остаётся основным и не меняется; поток нужен внешнему сборщику (Loki,
Elastic, Splunk), которому нельзя доверить доступ к БД или нужна независимая копия.

```json
{"type":"audit","level":"INFO","msg":"audit","time":"2026-11-01T10:00:00Z","user":"alice","role":"admin","action":"DeletePod","result":"ok","detail":"namespace=default name=nginx","source":"203.0.113.9","teamId":"t1","clusterId":"c1"}
```

- stdout содержит **только** строки аудита, журнал процесса идёт в stderr: сборщик может разделить потоки.
  Строки аудита отличает и поле `"type":"audit"`.
- Запись попадает в поток, даже если хранилище аудита отказало (ошибка записи в БД видна в интерфейсе
  как `writeError`); отказ самого потока на действие не влияет.
- Поле `detail` проходит тот же редактор секретов.
- Для административных команд (`kubron-server rekey` и др.) зеркало не включается: их stdout — результат
  команды.
- Хранение и срок жизни — на стороне сборщика; журнал в БД ротируется отдельно.
